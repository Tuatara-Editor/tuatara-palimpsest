palimpsest Manual

for Tuatara 0.90.44 and later, every chapter on one page

This manual is written with modal editing on, first and foremost. Where a command also has a key that works with modal editing off, it is given as well, as the non-modal key.

What palimpsest is

A package that takes a PDF apart, save by save, and looks for signs of editing.

A palimpsest is a page that was written over: the old writing is scraped off, and it still shows under the new. A PDF is often like that. When a program changes a finished PDF it can add the change at the end of the file and leave what was there before, so the earlier text is still in the file. Other edits leave other traces: a date that cannot be right, a white box over a figure, a character copied over another in a scan. palimpsest reads a PDF, or a picture of a scanned page, and reports each save the file holds and every such trace.

It is a package, not part of the editor, and it is for people who must judge whether a document is what it says it is. This chapter says how to load it, what it reads, what it never does, and how much a finding can be trusted. The chapters after it cover each part of the report and each check.

1.1 Loading it

palimpsest is loaded like any package, with a line in your init file:

(load-package "palimpsest"
              :source "https://github.com/Tuatara-Editor/tuatara-palimpsest")

Save the file and start Tuatara again. Tuatara fetches the package the first time, offers to show you its source and asks whether to compile and load it. Answer y. After that it loads at every start. Chapter 19 of the main manual explains packages, signatures and updates.

To read scanned pages palimpsest needs three programs on the machine: bubblewrap, ImageMagick and poppler. On Fedora they are in the packages bubblewrap, ImageMagick and poppler-utils. A PDF with no scanned page needs none of them.

1.2 What it reads

palimpsest reads the octets of the file, with its own code. Octets are the bytes of the file. It does not hand the PDF to another program to open, and it follows the PDF's own structure: the cross-reference sections, which say where each object begins, the trailers, the objects and their streams, the pages and what they draw.

It examines two kinds of file:

  • a PDF, taken apart into its saves, which the report calls revisions;
  • a picture file (PNG, JPEG or TIFF), examined as one scanned page. A picture has no revisions, so the commands that write or show a revision say so (C-c o, C-c w, C-c t and C-c T). Its summary gives its kind and its size in pixels in place of a PDF version, and its * Checks lists only the checks of a scanned page. C-c s still saves the report and the fingerprint.

A place on a PDF's page is given in points from the page's bottom left. A place on a picture is given in the same points, one point to a pixel, and in pixels from its top left.

1.3 What it never does

Nothing in a file is run. JavaScript, actions that launch programs and addresses to visit are named in the report and never followed. Nothing the file names is fetched. The file is not changed, and nothing is written beside it: what palimpsest writes goes to a directory of its own in Tuatara's cache directory, readable by you alone. A directory named in *evidence-directories* refuses every write, as the main manual's chapter 12 says, so nothing palimpsest makes can land in one.

The file itself is read in a Tuatara of its own, shut in a sandbox, a wall that lets a program read what it is given and write nowhere else. That Tuatara has a limit of memory and of time, so a file made to fill the memory stops there and never ends the editor (chapter 9). Pictures in a scanned page are decoded there too, each by a program held to its own files. A page kept as fax or JBIG2 is drawn by poppler's pdftoppm in the sandbox, from a PDF of that picture alone. Only the pictures of scanned pages are decoded; no page is ever drawn as a picture to be compared.

What the report quotes from the file, such as a producer, a signer's name or text from a page, is written with each control character shown as Tuatara shows it on the screen, an escape as ^[ and a bell as ^G. Reading a kept report with cat in a terminal cannot move the cursor or hide a line, whatever was written into the PDF.

1.4 A sign is not proof

Every finding says that something in the file looks like a trace of editing. None of them says who edited the file, or that the edit was wrong. Honest files have later saves, programs that edit PDFs, fonts in two subsets, scans with uneven ink. Each finding names the honest causes it knows, so that you can weigh them. Chapter 6 says how the strengths are given and how to read a finding.

Two things palimpsest cannot do, and you must not expect of it:

  • find an earlier save that was erased without trace. A file written again in one go, with nothing of the old text in it, has no earlier save to read;
  • say that a file is genuine. "No sign of editing found" means that none of its checks found one, and a careful hand leaves few.

Chapter 9 lists the other limits, and chapter 7 what each check can and cannot tell.

Try it, loading palimpsest and opening a report

  1. Add the load-package line above to your init file with C-x C-f on ~/.config/tuatara/init.lisp, and save it with C-x C-s.
  2. Restart Tuatara. To the question about compiling and loading palimpsest, press v to read its source, q to come back, then y.
  3. Open a PDF of your own with C-x C-f.
  4. Run M-x palimpsest. A buffer named after the file opens and says it is examining. In a moment the report replaces that text. Chapter 2 reads it.

Examining a file

Running palimpsest on a PDF or a picture, and reading the report it makes.

M-x palimpsest examines one file and shows the result in a buffer of its own. The report is long on purpose: it says what was found, where, and how to see it again by hand. This chapter covers how to start an examination and what each part of the report holds. Chapter 3 goes on to the revisions and objects the report links to.

2.1 Starting an examination

palimpsest examines the file the current buffer shows, when its octets are a PDF: a PDF's page view, a PDF visited as text, the PDF on a line of rimu or of the directory editor. When the buffer is not one of those, or always with C-u, it asks PDF to examine:. A picture file (PNG, JPEG or TIFF) is examined too, as one scanned page.

It refuses what is not a file, and what does not begin as a PDF does (the file does not begin with %PDF-).

The work runs in the background, as a job, and the editor never waits. The letter P is lit in the report's mode line meanwhile. C-x j lists the job, Examining NAME for signs of editing, with what it is doing and how far it has got. C-x J stops it, at once, even in the middle of a page that draws millions of operators.

The file is not read in the editor. It is read in a Tuatara of its own, shut in by the sandbox, as a mailbox is read: that Tuatara sees the file, read only, and the report's own directory, and nothing else of yours, and it has a limit of memory and of time. It sends back what it found, and the editor makes the report from that. Showing an object (C-c o), drawing a copy and comparing files work the same way, one file to each Tuatara. Chapter 9 says what happens at the limits.

The report is a buffer of its own, *Palimpsest: NAME*, read only. A file is examined once while its report is open: palimpsest on it again shows the report as it was. To examine a file again after it has changed, close its report first with C-x k.

The verdict weighs only the strengths of the findings. It reads Strong signs that the file was edited after it was made. when any finding is strong, Signs worth a look, none of them strong. when the strongest are worth a look, and No sign of editing found. otherwise. Read the findings before you rely on it.

Not read lines keep a report from seeming more complete than it is. They say that the file does not begin with %PDF- in its first 1,024 octets; that it has no %%EOF line, so its objects were read as one save; that it holds more objects, saves or decoded data than the limits of chapter 9 allow, so the rest were not read; or that a page's content stream could not be read, naming the revision and page and the cause, such as it is encrypted. A page that cannot be set beside the save before is named too. The rest of the examination goes on: one page never ends it.

Once any save names /Encrypt, every string and stream of the file is taken as encrypted, those written before that save too, as a PDF reader takes them. They are not decrypted, so the content of such a file's pages, fonts and pictures is not read. How the file is put together, its saves and its cross-reference sections still are.

2.2.2 The checks

* Checks has a row for each check that runs on this kind of file. The row's name is a link: RET on it opens, in a help buffer, what the check looks for, how it finds it and what honest files can show alike. The rest of the row says how the check went:

  • the strongest finding it made, with what it counts (characters, regions, patches, else findings) and the pages;
  • none, when it ran and found nothing;
  • not run, with the reason (no scanned pages, no text layer, no pictures, not a JPEG, no pages, no known-genuine files given), when the file has nothing for the check to read. Such a check says nothing either way;
  • could not finish, when it failed on what the file holds. A finding for the record says why.

Chapter 7 lists the checks.

2.2.3 The findings

Under * Findings the findings are grouped by strength, the strongest first, each group headed with how many it holds: ** Strong signs of editing (2), ** Worth a look (4), ** For the record (1). Within a group they go by revision, then page; but those worth a look go in three parts first: signs no honest file measured showed, then signs on a place worth changing (an amount, a date, a number, a field's label), then the rest. A finding about the whole file is put in the latest revision.

A finding worth a look of a kind honest files show too ends with a sentence of its own: how many of the 1,445 honest files measured show it, and its known honest causes (a curled or tilted page, a second JPEG save, bold type, a stamp, a form's second ink). A kind no honest file showed says nothing more.

Each finding is a line beginning with -, which says what was found and what it means in one sentence. A strong one is shown in the colour of warnings. Under it come:

  • where: the revision, the page when the finding is about one, and the objects it concerns. Each number is a link, and RET on it shows the object as that revision has it (chapter 3). Past 20 of them it says and N more;
  • its details when it has any: the text before and after, what is drawn, the programs named, each on a line of its own.

The logs of chapter 3 hold more for each finding: the rule that found it, the evidence and the steps to see it again by hand. When a check fails on a damaged file, the others still run, and the failure becomes a finding of its own, for the record: The check of NAME could not finish on this file: WHY.

2.2.4 Methods and fingerprint

Each finding names the way of editing it plausibly comes from: a white box over text, figures retyped in another font, characters cut out of a scan. * Methods lists those ways, the most practised first, each with what shows it and the findings that do. Above them a line gives the craft they take, on four levels:

Table 2.3. The craft of editing.

editor's text tool.

The levels rate what was found, never what was not. A careful hand leaves fewer signs, so a file that shows level 1 may have been worked on with more craft. A way shown only by signs worth a look is marked (signs worth a look only). The craft line gives the level the strong signs show, and says so when signs worth a look alone show a higher one. When none of the signs is strong it gives no level as shown: it says so, names the highest level the signs worth a look would take, and that an honest file can show as much.

* Fingerprint holds what tells of who edited the file and with what:

  • method: each way of editing found;
  • editor: each program a later save names that the original does not;
  • made-by: the programs the original names, which made the document and did not edit it;
  • index: how a later save keeps its cross-references, as a table or a stream;
  • jpeg: the quantisation tables each JPEG picture was saved with, by a short name of their own and the quality they stand for. A scanner's software saves with its tables. Someone who opens a scan and saves it again saves with their editor's, and those stay with the file.

C-c s writes the fingerprint to a file of its own, which chapter 5 uses to group files into cases.

Try it, reading a report

  1. Examine a PDF of your own with M-x palimpsest.
  2. Read the * Summary. Note the verdict and the line Findings.
  3. Press TAB until the cursor is on a name in * Checks, and press RET. The help buffer says what that check looks for. Press q to close it.
  4. Search for a finding with C-s and read its revision, page and objects.
  5. Press C-x k to close the report. If you have not saved its copies it asks first.

Revisions and objects

Reading each save of the file, looking at its objects, and keeping the work.

A PDF that was changed after it was made often holds the earlier versions in itself. Each save is a revision. palimpsest lists every revision, shows any object of any revision, writes each revision out as a PDF of its own, and writes a log for each that another examiner can follow with a hex editor and nothing else. This chapter covers those parts of the report and the keys that use them.

3.1 The revisions

Where a thing is drawn, the report gives its place on the page in points from the page's bottom left: text, filled shapes and pictures each get one.

Objects written again with the very same octets are not listed here. The log lists them.

Two pages are set beside each other when they are the same page object, the same number, in both saves, or else when they are at the same place. Two things drawn are the same when they are of the same kind and text, at the same place and size to the nearest point, of the same colour to a twentieth and in the same render mode. So text moved by a point or recoloured slightly shows as gone and new.

What is laid over a page is set beside the save before too: each annotation gets a line with its kind, what it says, a form field's name and value, a shape's fill, where it lies and whether it is hidden, shown under "laid over". A save that only lays a text box and a stamp over a total, the page's own operators untouched, shows them there as added.

3.2 Showing an object

Any object can be shown, read only, in a buffer of its own:

  • RET on an object's number in the report shows it as the revision it is listed under has it;
  • C-c o asks Object number (N):, offering the number at the cursor. It shows the object as the revision whose part of the report the cursor is in has it, and anywhere else as the latest save has it. Which revision the cursor is in is told by the report's own headings, never by anything the PDF says;
  • C-u o does the same and shows a stream in hex whatever it holds.

The object is read in the background, so the report can be used meanwhile.

The object's buffer, *Palimpsest: NAME object N, revision R*, says:

  • where the object is: where it begins and ends and the revision that wrote it. An object packed in an object stream is placed by the stream and the offset of its decoded octets. It is not in this revision. means it was freed or not yet made;
  • what it is to the document, when that is known: a page's content, the catalogue, the page tree, the document information, the XMP metadata, the form, a font, a picture, an annotation, a form field. Otherwise what its /Type or /Subtype says;
  • its dictionary as written, octet for octet, up to 64 kB;
  • for a stream: its size in the file, where its data is, its filters, and how much it decoded to, or why it was not decoded (picture data (/DCTDecode), not decoded, it is encrypted). Then come the decoded octets as text, or, when they are not text, a line In hex: and the name of a buffer that shows them in the hex view, shown at once. At most *palimpsest-largest-shown* octets of a stream are shown (1 MB as standard), and the rest is counted.

3.3 The logs

For each revision palimpsest writes a log, revision-N.log, beside the revision's PDF. RET on its name in the report opens it, read only, and q closes it. It is written so that someone else can do it all again by hand. Its parts:

  1. its head: the source file's name, size and SHA-256, when the log was written and by which version of palimpsest;
  2. how the revision was found: where its %%EOF is, where its startxref is and the offset it names, the kind and place of its cross-reference section, its trailer in hex and as text, its /Prev, anything not as it should be, the revision's octets, the SHA-256 of revision-N.pdf and how to check it: copy the source file's first N octets into a new file and compare sums;
  3. the signs found in this revision, each numbered with its strength, words, page and objects and then the Rule that found it in one sentence, the Details, the Evidence (offsets in hex and decimal, with the octets in hex and as text, a full stop standing for an octet that is no printable character) and the Steps to see it by hand;
  4. the objects: what the revision adds, changes, writes again unchanged and frees, with where each is;
  5. the changes against the revision before: for each page the text lines gone and new, the annotations gone and new, and each thing drawn now and before, with the operators that draw it and their place in the decoded content stream.

The same file always gives the same log, but for the line saying when it was written, so two examiners' logs can be compared. An offset in the decoded octets of a stream counts from the first octet of the decoded stream. For a stream with no filter that is the stream's octets in the file.

3.4 Keeping the work

When a report is made, each revision is written out as revision-N.pdf: the file's octets from its start to the end of that revision's %%EOF line, the document as it stood after that save. The log goes beside it. They go to a directory of the report's own, under palimpsest/ in Tuatara's cache directory, with the files read only. Nothing is written beside the PDF examined.

That directory belongs to the report. Closing the report deletes it with what is in it, and one left behind when Tuatara ended without closing the report is deleted at the next report after a day. To keep the work, save it.

C-c s saves everything: every revision, its log, the report as NAME-revision-report.txt and the fingerprint as NAME-fingerprint.txt, to a directory you name. The directory is made when it is not there. The copying runs in the background and each copy's SHA-256 is checked against its original. The report ends with a part * Saved saying where each copy is, the summary gains a line Saved to, and closing the report no longer asks.

Many files

Setting a directory of PDFs beside each other, grouping files into cases, and setting a questioned file beside known-genuine files of its issuer.

Forgery rarely stands alone. The same signature picture turns up in several contracts, one stamp on many pages, one editor in a pile of invoices. Two commands look across files. palimpsest-compare-files reads a directory of PDFs and finds what is the same in two of them. palimpsest-group-cases reads the fingerprints of reports you saved and groups the files that look made by one hand or one kit. palimpsest-compare-genuine sets the file of a report beside documents of the same issuer that you know to be genuine. This chapter covers the three.

5.1 Comparing a directory

palimpsest-compare-files asks for a directory and sets beside one another the PDFs in it, not those in the directories under it, to find a signature, a stamp or a seal that is the same in two of them. Pictures that are not scans are set beside one another by their octets. The marks of the scanned pages that are as large as a signature or a stamp are laid over one another pixel by pixel, as palimpsest does within one file.

It lists the pictures that are in more than one file and the pairs of marks of two files that are the same. The message says how many PDFs, how many pictures in more than one and how many pairs of marks. It needs two PDFs or more, and reads at most 200 of them; the list says how many more it found. The files are only read. The work runs in the background and takes as long as examining each of them takes.

noneM-x palimpsest-compare-filespalimpsest-compare-filesSet beside one another the PDFs of a directory asked for, to find a signature, a stamp or a seal the same in two of them.

No hand signs twice alike and no stamp presses twice alike. But an office's logo, or a signature it keeps as a picture, is honestly the same in every letter. Whether the marks should differ is for you to judge.

5.2 Cases

5.3 Beside known-genuine files

A document written again from nothing agrees with itself. It still differs from what the issuer's own system writes. With one genuine file there is no such measure, and only a page with more than half its runs off the grid is named.

Two or three are enough to read the issuer's habits; more make them surer. Beside one genuine file alone, a genuine document of the same issuer was worth a look once in twenty, for a size of text, a font or a picture the one file lacked; beside several, never. A scan can be set beside scans from the same machine: the JPEG tables and the scanner's way of writing the PDF are habits too. The examined file's pixels are not set beside the genuine files' pixels.

Strengths and how to read a finding

What STRONG, worth a look and for the record mean, and how to weigh them.

Every finding has one of three strengths. The strength says how far an honest program could have left the same sign. It does not say how much was changed or how wrong it is. This chapter says what each strength means, how the strength is chosen, and how to read a finding with its honest causes before you decide.

The first is the one to read first. A strong sign is a fact of the file that an honest program does not produce, not a judgment about the document. A strong sign can still have an honest meaning in your case: a stamp laid over a page in a later save is how a viewer signs a contract, and chapter 8 shows that. Say what was found, and say why it is or is not what you expected.

6.2 How the strength is chosen

The strength belongs to the rule that made the finding, sometimes raised by what was found. The same covering shape is a strong sign when it is white and worth a look in another colour. Invisible text is for the record over a scanned page and strong when a later save added it. Chapter 7 says, for every check, when its findings are which.

How far a measure is off never sets the strength. The least amounts a rule names (30 grey levels of ink, 1.5 pixels, a tenth of a size) decide only whether a finding is made. A run of text in a size of its own is worth a look whether it is a tenth smaller or half, as a heading or a footnote is too. What raises a finding is a sign honest programs do not leave: pixels the same where no scanner makes them so, or a structure no program writes.

A scanned or photographed word unlike its line is never strong, however many ways it is unlike it, for a real scan has such words too. When two measures apart from each other agree on one, so that it looks unlike its line and sits off it, the finding says so, and it stays worth a look.

A fact of how the file was made is for the record, said once however many fields or ways show it: a later save kept, a PDF editor named, a picture kept otherwise than the others, a JPEG saved twice. Honest files show each as often as edited ones, and none of them points at a place. What a later save changed is the sign, and that stays worth a look.

A sign is for the record too where the honest files measured show it as often as the forged places do, and it was found at no forged place alone: a word off its line by its baseline alone by more than 5 pixels, a block of lines set apart, near pairs of pieces or on a page naming more than five, the lines a file sets apart throughout, hidden text of fewer than three letters. Each is noted with its place, for the examiner to look at when the case asks.

6.3 Where a sign lies

A forger changes what is worth changing: an amount, a total, a date, a name, an account or reference number, an IBAN, a signature, a form's filled field. An honest scan's quirks fall anywhere. So where the page's text can be read there (its own text, or a scan's text recognition), a sign is weighed by the line it lies on. A line holding a figure or the label of such a field is a place worth changing, and a sign there stays worth a look. A line of five words or more without either is running text or boilerplate (terms and conditions, a letter's body, a printed notice): a sign of a kind honest files show too lies there as a note, which says that honest pages show it and that a change there would serve no one. A short line without figures may be a name or a heading, and a scan without text cannot be read at all; a sign there stays worth a look. A sign no honest file showed stays worth a look wherever it lies.

A finding worth a look of a kind honest files show says so in a sentence of its own: how many of the 1,445 honest files measured show it, and its known honest causes. Weigh it against them before deciding.

Strong signs need the file to contradict itself: a startxref naming a section outside its save, a length that runs over a save of the file, a date before the file was made. A file that does not contradict itself gets, at most, a worth a look.

6.4 The verdict and the order

The verdict in the summary is the strongest strength found. The findings are listed strongest first, then by revision, then by page. Those worth a look go in three parts first: signs no honest file measured showed, then signs on a place worth changing, then the rest. Each is put in the revision it is about, or, when it is about the file as a whole, in the latest.

6.5 Reading a finding

  1. Read the sentence. It says what was found and what it means.
  2. Read where: the revision, the page and the objects. RET on an object number shows it as that revision has it. C-c d draws the page with the object framed.
  3. Read the honest causes. A finding that can come from honest programs names them, for example heavy type in a scan, a stamp or a clipped scanner. Open the place it points to and see whether one of them fits.
  4. Open the revision before (chapter 3) and compare it with the last. The report sets the text of each changed page side by side.
  5. Open the log for the finding to see the rule, the evidence and the steps to check it by hand.
  6. Weigh what is outside the file: the other party's copy, the paper, how the file reached you.

6.6 Checks that could not finish

In the log each finding names its check, and the * Checks part of the report sums the findings up by check.

A check that could not finish says so, for the record. Treat that as a limit, not as a clean result: what the check would have read was not read.

  3. For one finding worth a look, read the honest causes in its sentence and open the object it names with RET.

What palimpsest looks for

Every check, what it reads, and what honest files can show alike.

palimpsest runs a number of checks on a file. Each looks for one way of editing that an examiner knows by name, and each is a row of * Checks in the report. The paragraph for each check below is the explanation that RET on its name in the report opens. It says how that editing is done, what it leaves, how the check finds it and what honest files can show alike. Under it come the strengths its findings take (chapter 6) and the files it is run on.

The checks run in the order of this chapter. Each runs on its own: when one fails on a damaged file, the others still run. Every check but those on pixels reads the PDF's objects, their dictionaries and the octets as written, and the operators in the content streams. "Ink" there is a colour as an operator gives it, a number.

Some checks are not run when the file has nothing for them to read. The row in * Checks says not run and why, and it says nothing either way about that kind of editing.

7.1 How the file is put together

These checks read the structure of the file: its saves, its indexes, its objects and the octets between them. They run on every revision of a PDF and not on picture files.

7.1.1 Later saves

A PDF can be changed without writing it anew: the program adds what it changes at the end of the file, a later save, and leaves the original before it. Most editing of a finished PDF leaves such a save behind. The check counts the saves the file keeps and names each page a later save changes, so that the revisions can be set side by side. Honest files have later saves too: a form filled in, a signature added, a reader's notes or a viewer that saves on closing all write one.

That the file keeps later saves is a fact of how it was made, said once for the record. What a save changed is the sign: a page whose text or drawing differs from the save before is named, page by page.

Strength: Worth a look for each page a later save changed. For the record for the later saves kept.

Runs on: a PDF.

7.1.2 Cross-reference sections

Each save ends in a cross-reference section, the file's index of where each object begins, and a trailer naming the section before it. Editing a file by hand, or with a tool that patches it in place, leaves an index that no longer fits: entries pointing beside the object they name, a section naming no earlier one, a save indexed in another way than the first, or a file prepared for fast web viewing changed after. The check reads every section against the octets of the file. Some honest programs leave empty slots in their index, and many store later saves in compressed object streams; those are named worth a look or for the record only.

In the first save, entries that name objects written nowhere in the file are empty slots, as cairo and Quartz leave in their index; that is for the record. An entry that misses an object written elsewhere in the file, or any wrong entry in a later save, stays strong. A startxref that names an offset where no section is is the same fault for the whole index. A save whose cross-reference is of another kind than the original's, a hybrid file and a linearised file that was changed were saved by another program than made them.

Strength: Strong for a startxref naming a section outside its save or none found, a save prepared for the web whose two parts disagree, and entries that do not point at the object they name. Worth a look for other problems with the sections and a save indexed another way than the first. For the record for empty slots in the first save's index, a linearised file changed later, hybrid files and changes kept in object streams.

Runs on: a PDF.

7.1.3 Objects freed, unused or written twice

A PDF is made of numbered objects. Removing or replacing something frees objects, or leaves them in the file with nothing using them; an edit done in haste writes an object twice in one save or reuses a number without raising its generation. The old objects keep what was there before. The check follows every reference from the document's root and lists what nothing reaches, what is freed and what is written twice. Programs that save carelessly also leave unused objects, so these tell where to look rather than prove an edit.

What a save removed is still in the file. Reusing a number without raising its generation is not what writers do. Objects that no reference reaches are leftovers of earlier content, or objects kept to be used later (see shadow attacks under Signatures). Objects written but listed by no section are hidden from every reader, or left by an edit. An object written twice in one save was written by hand or by a careless program.

Strength: Worth a look for objects no section lists, objects written twice and numbers used again without a higher generation. For the record for unused objects, which writers leave as often as editors do, and freed objects.

Runs on: a PDF.

7.1.4 Data before and after the file

A reader of a PDF looks for its first line and its last %%EOF and skips anything outside them. Data appended after the last save, or put before the file begins, is a place to hide a message or an earlier version. The check reads what lies beyond those ends and says what it is. A file sent by mail or copied from a disc can carry a few honest octets of padding there, which are named as such.

Data there may be hidden data, a save cut short, or a file made to be read as two kinds. A few lines of comments shaped as a printing system's banner page (up to 1 KB, each beginning with %) are for the record: CUPS carries its instructions so. Printer job lines are worth a look. One octet repeated (padding) is worth a look. 64 octets or more mixing kinds of white space (NULs, tabs, form feeds, spaces, line ends) are strong, and the finding names and counts the kinds.

Strength: Strong for 16 octets or more after the last %%EOF that are not shaped as a printing system's banner or printer job lines, for PDF objects there, and for a kilobyte of white space. Worth a look for a few octets, printer job lines, padding of one octet repeated, and octets before %PDF-. For the record for a banner.

Runs on: a PDF.

7.1.5 White space hiding data

Between a PDF's objects any amount of white space may stand, and a reader skips it. A program hiding a message can write it as a pattern of spaces, tabs and line ends there. The check looks for long runs of white space within the saves that mix their kinds as such a code writes them. Writers pad with runs of one kind; a run of spaces between two line ends is not named.

A run counts when it lies outside the data of the streams: between objects, after a stream's data, between the trailer and startxref, or between startxref and %%EOF. It is named when it is 64 octets or more long and mixes two kinds besides line ends, eight or more of the second, as after the last %%EOF, with the kinds named and counted. Line ends of any kind, what strings and comments hold, and the data of a stream whose end is not where its /Length says are left out. Of some 13,900 honest PDFs none held such a run: writers pad with one kind, and end and indent lines as they please.

Strength: Strong for a run of 64 octets or more of white space mixing its kinds, anywhere in the file outside the streams.

Runs on: a PDF.

7.1.6 Saves hidden in streams

A stream holds a page's drawing, a picture or a font, and its stated length tells a reader where it ends. A save can be hidden inside a stream whose length is written to swallow it, or a stream left open so that a reader passes over the save that follows. The check sets each stream's stated length beside where it really ends, and looks for %%EOF lines and object headers inside the data of streams that are not embedded files. A PDF kept inside another as an attachment holds those honestly, and is not named.

A stream whose /Length disagrees with where endstream is was changed by hand, or by a program that did not write the length again.

Strength: Strong for a stream whose /Length runs over a save of the file itself. Worth a look for a %%EOF within a stream whose end the file does not confirm, and for %%EOF or object headers within the data of a stream that is no attached file.

Runs on: a PDF.

7.1.7 Comments between the objects

Lines beginning with % between a PDF's objects are comments, which no reader shows. Some editing tools write their name there, and some people hide notes in them. The check lists the comments and the programs they name. Several honest writers leave a comment of their own as well. Two are named as editors: ExifTool, which marks each change it makes to what a file says of itself with a pair of comments, and the QDF form of qpdf, a way of writing a file out so that its pages can be changed by hand in a text editor. A finished document left in that form was opened for that.

Strength: Worth a look for comments naming an editor. For the record otherwise.

Runs on: a PDF.

7.2 What the file says of itself

These read the file's own account of its making: its dates, its programs, and any credentials. They run on a picture file too.

7.2.1 Metadata and dates

A file says of itself which program made it and when it was made and changed: in a PDF, its document information and its XMP metadata; in a picture, its EXIF, XMP and other fields. An editor writes its own name and a new date, or forgets to change one of two places that should agree. The check reads every field, sets the dates against each other and against today, and names programs that edit files. Dates differ honestly by time zone, and a picture turned or cropped in a phone's gallery is saved again with a new date, so these are worth a look at most unless they cannot be true.

A document's information and its XMP that disagree show that one was changed without the other: dates, producing and creating programs, title. A date last changed before it was made, a date in the future and a time zone no place uses are a date set by hand, or a clock set wrong. Changed before made by a gap an honest clock can leave is worth a look: dates in two zones up to 14 hours apart, an hour or less, or about 12 hours (a twelve-hour clock). Any other gap is strong.

An edit history in the XMP lists each save a program kept and the program that saved it. XMP's OriginalDocumentID or DerivedFrom names another document the file was made from. A producer, creator or XMP that names a PDF editor or online service is said for the record, each program once with every field naming it: iLovePDF, Smallpdf, Sejda, PDFescape, PDF-XChange, Foxit, Nitro, PDFelement, Soda PDF, pdftk, qpdf, PyPDF, PDFsam, Acrobat, Preview, Canva and the like. Honest files pass through such programs as often, a scan's text recognition in Acrobat among them; what the program changed is named by the later saves. A producer naming Acrobat beside a creator naming another program, and a document DerivedFrom another, are for the record too. A save that names another program, removes metadata or gives another first /ID was made by whatever program it names; clearing metadata, or another document's ID, is done on purpose.

The file's dates out of order between saves are for the record: a save giving another creation date than the save before (more than a minute apart, zones allowed for), a save last changed more than a minute before the save before it, or the XMP's MetadataDate more than a minute before its CreateDate. A program that sets the creation date anew on each save, or a clock that slipped, gives the same.

For a picture file, what the picture says of itself is for the record: the device (EXIF's make and model), the programs and dates it names, and every field of its EXIF, XMP, PNG text and time, JPEG comments and TIFF tags, read as data. A picture editor named is worth a look: EXIF's Software, XMP's CreatorTool or edit history, or a comment ("Created with GIMP") names GIMP, Photoshop, Paint.NET, Affinity Photo, Pixelmator, Krita, Lightroom, Snapseed, Picsart, Pixlr, Photopea and the like, the more so beside a camera's or scanner's own name. An honest crop, turn or lightening is saved so too, and some scanner and phone apps name such a program. A picture made and changed at different times is worth a look: when it says it was made (DateTimeOriginal, xmp:CreateDate) and last changed (DateTime, xmp:ModifyDate, a PNG's tIME) lie more than a minute apart, or more than 26 hours when one names no zone. A picture turned in a phone's gallery or saved again by a viewer gives that too.

The XMP names the toolkit that wrote it (x:xmptk). When that is a program that edits metadata, ExifTool say, and neither the producer nor the creator names it, the XMP was written anew after the file was made: worth a look. Archives and publishers add titles and keywords so too.

LibreOffice and OpenOffice write a checksum of the file into its trailer (/DocChecksum, the MD5 digest of every octet before the trailer). A program that writes the file again leaves the old checksum and changes the second part of /ID: for the record. A checksum that fails while the two parts of /ID are still alike, as LibreOffice writes them, is strong: the octets were changed where they lay, by no program that says so. That is how a file is changed by hand to look untouched. A forger who works out the checksum again leaves no such sign.

Strength: Strong for a date last changed before it was made, a date in the future, the document information and the XMP more than a day apart on a date, and LibreOffice's checksum failing in a file whose /ID parts are alike. Worth a look for other disagreements, odd time zones, edit histories naming an editor, another program in a later save, XMP written by a metadata editor, metadata removed and the first ID changed. For the record for a PDF editor named, a file saved again in Acrobat, a document derived from another, two time zones, dates compared only to the month or year, and the two parts of /ID differing.

Runs on: a PDF or a picture file.

7.2.2 Content credentials and generator marks

Some programs record how a picture or a document was made: content credentials (C2PA), the digital source type in XMP, and the marks image generators write. The check reads them, as data and nothing more, and names a picture an image generator says it made, or a later edit the credentials record. Credentials can be stripped, so their absence says nothing.

A picture says an image generator made it, or a part of it, when its content credentials (C2PA, in a JPEG's APP11 segments, a PNG's caBX chunk or a TIFF's tag 52545) have an action whose digital source type is trainedAlgorithmicMedia or compositeWithTrainedAlgorithmicMedia, or name a generator as the program. (algorithmicMedia alone is said as made by a program, as a fractal is; a generator named only in the credentials of a file it was made from is said as a part made so.) It says so too when its XMP's Iptc4xmpExt:DigitalSourceType does; when a PNG keeps a generator's own text (Stable Diffusion's parameters, ComfyUI's prompt and workflow, InvokeAI's, SwarmUI's, NovelAI's settings); or when Software, CreatorTool, an edit history or a PNG's Source names Midjourney, DALL-E, Adobe Firefly, Stable Diffusion, NovelAI and the like. Names in comments and descriptions are passed over.

A file keeping more than one store of credentials has every store read, the last manifest of the last taken as its own, and that is recorded. The picture's size is named beside the finding when generators often make it (1024 by 1024, 832 by 1216 and so on), never alone. The finding tells how the picture was made, not that the document is false. The credentials' signer and its certificate's issuer are named as written, and the signature is not verified. In a PDF the same is worth a look for credentials kept in an attached file (relationship C2PA_Manifest; every attached file is looked at), for the XMP's digital source type, and for a JPEG picture's own credentials and marks.

Content credentials that name no generator are for the record: what they say (the program, the actions and their digital source types, the files it was made from, the signer), as written and not verified. A pointer to credentials kept elsewhere (dcterms:provenance) is recorded, not fetched. Most generated pictures carry no credentials or marks at all, so none found says nothing.

Strength: Worth a look, never strong, for a picture or PDF that says an image generator made it. For the record for content credentials that say nothing of a generator.

Runs on: a PDF or a picture file.

7.3 What the pages draw

These read the instructions that draw each page, its fonts and its pictures, in the latest revision. The earlier pages are compared in the revisions' parts of the report.

7.3.1 What the pages draw

A page is drawn by a list of instructions. Editing text in a PDF often leaves the old text under a white box, makes it invisible, clips it away, moves it off the page, or adds new text drawn a character at a time in a font of its own. The check reads every page's instructions and looks for text covered, hidden or clipped, text appended later, figures placed unlike their font's widths, table cells set apart from their column, tagged text unlike what shows, and words a chatbot leaves in pasted text. Some honest programs also draw a character at a time or leave text under shapes, so most of these are worth a look rather than strong; a file that sets more than two lines, runs or figures apart sets its text so throughout, and they are said once for the record.

A white shape of any outline over text is strong, and the covered text is named. A shape of another colour is worth a look (a black one is a redaction drawn over text, the text still in the file). Worth a look too, with its cause named, is an office program's text box drawn as the file was made, a panel over a watermark, an outlined callout, labels over labels and a stamp at a slant. Invisible text is text in render mode 3 or 7; over a picture of the whole page it is a scan's text recognition, recorded and set against the picture. Tagged text unlike what shows is /ActualText or /Alt saying that the text stands for something else. A page of several content streams, one appended later, had something laid over it by a later save.

A figure placed unlike its own font's widths is worth a look, never strong: four or more characters of a figure in a row, two different pairs or more among them (one pair kerned again and again, as Helvetica kerns "1 1", is not named), each moved on by 30 thousandths of the size or more, the same way, beyond what the font's /Widths give (TJ numbers, or a move of its own before each character), where at least 90 % of the other steps within words on the line keep to the widths. A program places each character where the one before ends and moves the text on only to kern a pair or spread the spaces; a figure placed for other widths was set again with another font, or at the positions of the figures it replaced. Text in fonts that give no widths (the standard fonts written without them) and fonts placed unlike their widths all over the page are left out. On the honest run of 977 files (62 PDFs written by programs, 70 real documents, 845 honest scans) and 85 more born-digital PDFs (LibreOffice, LaTeX, Skia) none was named.

A cell of a table set apart from its column is worth a look: a figure in a column of four or more (figures a size or more apart from the words beside them, their right edges or decimal points within 0.3 points) set in another font, size or dark ink than every other figure of the column, those alike, and than the rest of its row. Left alone: a row set apart as a whole (a bold total, a header), the column's own family in bold or italic (a best value set off), red negatives and highlights, a cell spaced apart unlike its column (a font's table of glyphs), a column of single figures, and fonts that give no widths. Of the same honest files one names two figures of a table, in a manual of fonts set by TeX, among many lines that file sets apart, so for the record (see below).

Words a chatbot leaves are worth a look, never strong: the page's text (its text recognition over a scan too) keeps what a chatbot writes about itself ("As an AI language model", "as of my knowledge cutoff", "som en AI-språkmodell"), the labels of its page copied with an answer ("Regenerate response", "ChatGPT said:"), its citation marks (oaicite, †source) or the tracking part of the links it gives (utm_source=chatgpt.com), each quoted with its page. Whole phrases of a fixed list are matched, a phrase broken over two lines too. A bracketed place left to fill ("[Insert date]", "[Your name]", "[Infoga datum]") is named as well, and said to be what an office template leaves too. A page that quotes a chatbot keeps the same words.

A number whose check digit fails is worth a look, never strong: a Swedish organisation number (also inside a VAT number, SE and its ten digits and 01), personal identity or coordination number, bankgiro number or OCR payment reference whose last digit is not the check digit by the modulus 10 method, or an IBAN that does not give remainder 1 modulo 97. So are a plusgiro number and a payment card's number (modulus 10), a Norwegian KID (modulus 10 or 11) and a creditor reference of ISO 11649 (RF and two check digits, modulo 97). Each is named with its page, the digit it should end in and the line it stands in. A number is taken only right after its label (Org.nr, Personnummer, Bankgiro or BG, Plusgiro, OCR, KID-nummer, Card number or Kortnummer, IBAN), written as such numbers are (556036-0793, 811218-9876, 5050-1055, 12 34 56-6, 1234 5678 97, SE45 5000 0000 0583 9825 7466), or with a label ending one line and its number on the next, under the label or after it (or alone on that line). An IBAN is taken after Account, Account number, Konto and Kontonummer as well, and a creditor reference after Reference, Payment reference and Referens, each only when written as one: any other account or reference number there is passed over, as no check is known for it. A card number with digits masked is not taken. Digits are not grouped across a gap between columns, and a ten-digit invoice or customer number is passed over. A personal number whose date cannot be is not taken, nor an IBAN of a length its country does not use, nor a number in brackets of its own after OCR, as a year cited after an office or text recognition of that short name is ("OCR (2023)"). A number read from a scan's text recognition is named for the record only, as text recognition may misread or drop a digit; the picture is not compared. Where a font draws other figures than copying gives, numbers are checked as drawn too, as a reader sees them. A slip in the issuer's own system gives the same sign.

A net and VAT that do not make the total are worth a look, never strong (for the record when read from a scan's text recognition): a page stating one net (Netto, Summa exkl. moms, Momsunderlag, Net), one VAT (Moms, VAT) and totals (Att betala, Summa, Totalt, Total, Amount due), each at the end of a line labelled so, of which no total is the net and VAT together within 51 öre (öre rounded to whole kronor). Only amounts with two decimals or written 1 250:- are read, their label holding no other figure than a rate. A subtotal is not taken for the net, as fees may follow it. A page with another amount between the net and VAT and the last total (a fee, a sum paid), with more than one net or VAT (several rates, several invoices), with a VAT over 27 % of the net, or with a line naming a weight, hours, a count, a discount or a sum paid is not checked.

A total that the amounts above it do not make is worth a look, never strong (for the record when read from a scan's text recognition). A forger changes the figure that matters and cannot change every figure that depends on it without forging more, and no way of saving the file again hides that. A line whose label says total, subtotal, summa or sum is set against the lines ending in an amount above it, back to the total before. It adds up when it is the sum of the last of them, however many, with or without the total before, or the total before less them, within 51 hundredths. A total over three amounts or more that does not is named, with the amounts and their places. A total that follows another with one or two amounts between (a subtotal, delivery, the total) is named only when it is one digit from what they make, as totals of other things stand so too (hours, then pay). Lists that hold an amount larger than their total, or below nothing, are passed over: a column of balances, payments taken off. A payslip's gross pay counts as a total of the payments above it. The same rule reads a column inside a table, one that does not end the lines: the amounts whose right edges stand within a point of each other are one column, and a total among four of them or more is set against those above it. So a payslip that lists payments and deductions side by side is read column by column. Where a printer has joined each line into one run, the edges are gone, and the amounts are taken as columns by their order in the line.

A net pay that is not the gross pay less the deductions is worth a look: a page stating each of the three once (Total gross pay or Gross pay, Total deductions, Net pay; Bruttolön, Summa avdrag, Nettolön), to the hundredth. Pay that is not taxed and is added after the deductions gives the same sign.

A running balance that breaks is worth a look. In a statement each row ends in its amount and its balance, and the balance is the one before it with the amount added or taken off. A page is read so when four rows or more follow one another. Three breaks are told apart, each named with its row and place: a row whose balance does not follow while the rows after follow from it (an amount changed, or this balance and every later one raised together); one balance that alone does not follow, the row after following from what it should be; and a line labelled the closing balance that is not the last row's balance. A row is judged only after a row that followed or a line labelled the opening balance, and a line that neither follows nor is followed is passed over as no part of the table. A statement whose every later balance was worked out again after the change follows throughout and shows nothing.

Figures are set against each other across the document as well, on its first 50 pages. A total carried forward at the foot of a page (Carried forward, C/f, Transport) is the total brought forward at the head of the next. A statement's running balance is followed from page to page: a row or a closing balance that does not follow from the last balance of the page before is named, with the honest cause that another account may begin on the page. A figure the document states as its one result (Amount due, Total due, Total to pay, Net pay, Closing balance, Att betala and their like) is the same wherever it is stated: a label stated with exactly two amounts is named, with each line. And where the document labels what is to pay, a sentence naming a sum to be collected or paid (by Direct Debit, please pay) names an amount the document states. A sentence is a line of running text, of more than five words, with no gap between columns and no amount ending it: a statement's row that names a direct debit is none. A file holding two documents, or a sentence naming an instalment, gives the same signs.

A weekday written beside a date that is not that date's is worth a look: Monday, 14 March 2026, when that day was a Saturday. The weekday stands right before the date (a comma, the or den at most between) or right after it (a comma or an opening bracket between), whole or short, in English or Swedish. Only a date whose day and month cannot be swapped is checked.

All of these read the text the file holds. A scanned page without a text layer has none, and none of them is run on its pixels: palimpsest does not read figures from a picture.

A row of a table that does not multiply out is worth a look as well: where three rows or more end in a quantity, a price and their product, a row whose amount is not its quantity times its price, when fewer than half as many rows fail as hold. Both checks read plain figures only (118.00, 1,250.00, 1.250,00). A slip in the issuer's own system gives the same sign, as does a table that lists other things than what its total adds.

A date in the text later than the file is worth a look, never strong: the date the page gives as the document's own (right after Fakturadatum, Kvittodatum, Dokumentdatum, Utfärdad, Invoice date, Receipt date, Date of issue, Issued, Dated, or Datum and Date with no word before them, the date beside the label or under it when the label ends its line or heads a column; or, in the upper half of the first page, a letter's date line, alone or after a place: Stockholm den 15 mars 2024) is later than every date the file gives of itself (the document information's /CreationDate and /ModDate in every save, the XMP's CreateDate, ModifyDate and MetadataDate), on the latest day any time zone had then: 14 hours ahead of a date that names its zone, 26 hours ahead of one that names none. Dates are read only where the day and month cannot be swapped: 2024-03-15 (also with a time after it, 2024-03-15T10:00), 15 mars 2024, March 15, 2024, 15.03.2024, 15/3/2024 or 3/15/2024, never 05/03/2024 or a year of two figures. A due date, a delivery date, a period (2024-03-01 – 2024-03-31) and a file date before 1993 are passed over. For the record: a date given only by Datum or Date, as agendas, invitations and tickets are often dated ahead of the day they are written; a date after the file was made but not after its last change; and a date read by a scan's text recognition (which may misread a figure), also when it is after the day the scanned picture's EXIF says it was made. A document dated ahead on purpose gives the same sign.

Only text that shows is set beside its line and its edge: invisible text, as a scan's text recognition lays it, is set as that program sets it, and is named by the check of hidden text instead. Lines and runs set apart from their line or their edge, figures retyped in another font, lines drawn a character at a time or spaced apart, figures placed unlike their font's widths and table cells set apart are each worth a look while the file names two of them or fewer in all. A file that names more sets its text so throughout: a manual, a font sample or a table set by TeX and the like. Then one finding says so for the record, with the count and the pages, and keeps each of them with its place. Two kinds stand outside that count: a figure in another font at the size of its line and on its baseline, and a cell in another font at its column's size. A superscript, a footnote's number or a label is smaller or raised; a figure set to pass for the line's own was set again. These stay worth a look while they stand on one page of the file. On more than one page they are a program's habit too (years and section numbers in a Latin font within Japanese text, say) and join the note. A run in a font the file does not keep, in a line whose other text is in fonts it keeps, where that font sets 40 characters of the page or fewer, is worth a look too: a program that keeps a page's fonts keeps them all, and tools that write over a redaction do not embed. A run set apart from its line, or a line off an edge, that lies in running text or boilerplate is for the record too (chapter 6, Where a sign lies). On the honest run of 977 files, the files with such a finding worth a look came from 66 to 6; the samples made for these checks change one run or one line, and each keeps it.

Text never seen (invisible, clipped, outside the page, in a layer that is off, white on white or under a point tall) of fewer than three letters and figures in all is for the record: specks of a text recognition layer, a mark a program left, or text of no characters. On the honest run 21 of the 29 such findings held fewer, 7 of them none.

Strength: Strong for a white shape or shading over text, invisible or white text added in a later save, and a content stream appended in a later save. Worth a look for covering shapes that are not white, text clipped, outside the page, in a layer that is off, white or tiny of three letters or figures or more, lines drawn a character at a time or spaced apart, retyped figures and runs, lines off an edge, tags unlike the text while the file names two or fewer, figures in another font set to pass for their line's or column's own, text in a font not kept in the file within a line of fonts that are, figures that no longer agree (check digits, totals, rows, net pay, balances, a figure stated twice, a weekday beside its date), and text on a scan. For the record for OCR text over a scan, several content streams from one save, hidden text of fewer than three letters or figures, and the text set apart of a file that names more than two.

Runs on: a PDF. Not run when: no pages.

7.3.2 Fonts and widths

Text typed into a finished PDF has to use a font, and the editor often brings its own copy: a second subset of the same face, the face both embedded and not, a family named the way another program names it, or the same font with other widths for the same characters. The check sets the fonts of the pages against each other. A document joined from parts made by different programs shows some of the same, so these are worth a look at most.

A font in several subsets is common in honest files: office programs, form designers and programs that print to PDF embed one font part by part. So it is for the record, unless a run of plain words or figures stands in a line set in another subset of the same font, kept in the same form. A program splits a font for characters its first encoding has no room for; plain figures in a second subset, within a line of the first, were embedded apart, as an editor does that sets a figure again. The run is named with its place. A font embedded on some pages and not others shows text set at different times or by different programs, or pages joined.

LibreOffice and OpenOffice number the subsets of a file BAAAAA, CAAAAA and on, each number once. The same number before two fonts, or before two copies of one font kept apart, comes from two exports: pages written in separate runs and joined, or a page put in from another file. The page set apart is named. A file that names one of these programs as its producer while its subsets carry other tags had its pages written by another program, and the producer's name kept or set: worth a look, named with the metadata.

A family named the way two programs name it on one page (ArialMT beside Arial; LiberationSans beside Liberation Sans Regular, the full name a program writes that embeds a font it found on the machine) was set by two programs. The runs in the name that sets less text are listed with their places. One font name with two sets of widths is worth a look: two embeddings of one font (two subset tags, or two font files), written in different saves of the file, that give other widths to two or more of the same characters, not figures alone. They are two versions of the font, from two machines or programs, or a stand-in for it, as when a later save sets text again. The text each draws is quoted. Left alone: one embedding written with two encodings (small capitals, old-style figures), two embeddings written in one save (a font split by cairo or Skia, OpenType alternates, two documents merged) and figures alone differing (tabular and proportional figures).

Strength: Strong for a font kept in the file that was last changed after the document was made. Worth a look for plain text set into a line in a second subset, a numbered subset tag given twice, subsets not tagged as the named producer tags them, a face embedded and not, a family named two ways, and a font on some pages only. For the record for a font in several subsets otherwise, and for a font that is both simple and composite.

Runs on: a PDF. Not run when: no text layer.

7.3.3 Text that copies as other text

A font maps each code to the shape it draws and, apart from that, to the letter it stands for when text is copied or searched. A figure changed by editing the font's map rather than the page shows one number and copies as another. The check compares the two maps of every font a page draws with. Old or badly made fonts can disagree honestly, so this is worth a look.

A figure or letter that copies as another than it shows is worth a look, never strong: a font's encoding names a code's glyph as one figure or letter (by /Differences, a name such as seven or uni0037, or by the WinAnsi or MacRoman encoding of a font not marked symbolic and, when it is a TrueType font kept in the file, holding a cmap from Unicode; a subset with only a cmap of its own codes is drawn by its codes, whatever encoding it names) while its ToUnicode map gives another figure or letter for it. The page shows one amount, and copying, searching and programs that read the text get another. Each font is named with its codes, the page and the text as it shows and as it copies. Ligatures, symbols mapped to private places, a letter in the other case and maps of several characters are passed over, as honest programs write them. Glyph names kept only inside the font program (a TrueType post table, a CFF charset) are not read, so a font of two-octet codes, or one with no encoding given, as LibreOffice and many others write them, is not checked.

Strength: Worth a look.

Runs on: a PDF. Not run when: no text layer.

7.3.4 Pictures unlike the others

A picture pasted into a document, such as a signature or a logo, often differs from the rest in how it is stored, its colours or the program that made it, or was added in a later save. The check sets the pictures of the file against each other and reads what JPEG pictures say of the programs that made them. Documents assembled honestly from many sources mix their pictures too, so a picture kept otherwise is for the record, and one added in a later save worth a look.

A picture with a compression, colour space, bit depth or resolution unlike the others is said once, for the record, with each way it is unlike them: pasted in from elsewhere, as a signature, stamp or logo is, or kept otherwise by the program that made the file, as a scanner keeps its layers or a grey page among colour ones; on the honest run 11 of the 13 files with such a picture were real scans. A picture added in a later save was put on the page after it was made. A JPEG picture keeping metadata of its own was made or edited elsewhere; its EXIF and comments are listed, read as data only.

A picture made after the file is for the record: a JPEG picture's EXIF says it was made (DateTimeOriginal, DateTimeDigitized) after every date the file gives, by more than a minute when both name their zone, else by more than 26 hours. It was put in later, or a camera's or scanner's clock was set wrong, as many are.

Strength: Worth a look for pictures added later, or keeping metadata that names a program. For the record for pictures unlike the others or of another resolution, and for JPEG metadata.

Runs on: a PDF. Not run when: no pictures.

7.4 Scanned pages

A scanned page is a picture of paper. These checks read its pixels, once for all: the scan itself is decoded and no page is drawn as a picture to compare. A picture covering a third of a page or more is decoded to grey levels, made black and white at the level that best parts ink from paper, straightened, its ruled lines taken out and cut into lines, words and characters. The checks that follow set each word and character beside the others. A picture file is examined as one scanned page, so they run on it too. None of them runs when the file has no scanned page, and the row of * Checks then says so.

7.4.1 Scanned pages read

The checks of the scanned pages read their pixels. This row says what could not be read or judged, so that no page goes unexamined without its saying so: pictures in a form not read here or too large, pages whose characters are too alike or too few to tell prints from copies, bands of lines run together, characters with too little ink left once clipped ink is set aside. Nothing here is a sign of editing; it bounds what the other rows can say.

A picture file is turned into pixels the same way, turned as its EXIF says it is held; a TIFF of several pages is read at its first. A page kept as narrow strips drawn one under the next is joined into one picture first (chapter 9).

Strength: For the record. It bounds what the other rows say.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.2 Pages drawn by a program

A scanned page carries the grain of paper and a scanner's blur. A page made by opening a document in a picture editor, or by printing it as a picture, is drawn by a program from text and has neither. The check looks for whole pages of perfectly flat paper whose text edges are smoothed into half-tones. A screenshot, a page printed to a picture by an app, or a scan whose paper was whitened until it is one grey look the same, so this is worth a look.

A page that is one picture drawn by a program (a PDF opened in a picture editor and saved again, its text turned to pixels) is named so: its blank paper is one grey and its text's edges are smoothed. A scan whose paper was whitened all over looks the same, and the finding says so. Saved as a JPEG, such a page, as "print to image", a fax server or a screenshot of a document makes one, has no grain of its own: the JPEG's rounding is all that makes two prints of a letter differ, and it rounds alike two prints drawn at the same place across a pixel that fall alike on its grid of 8 by 8 pixels.

Strength: Worth a look, never strong.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.3 Words unlike their neighbours

A word pasted or typed into a scanned page rarely matches the words around it: its ink is darker or lighter, its edges sharper or softer, its paper cleaner, or it sits off the line or turned against it. The check measures each word against those beside it and names those that stand apart, more so those apart both in how they look and in where they sit. Real scans have uneven ink, stains and folds, so these are worth a look at most; a word off its line by its baseline alone by more than 5 pixels, a word in running text or boilerplate, and a block of lines set apart together, as headings and shaded rows are on honest pages, are for the record.

A word whose ink, edges or paper differ from the words beside it, or that sits off its line or is turned against it, was pasted, printed over the scan or moved; a stamp, a form filled in and a line printed in another pass do the same. Each character is set beside its line too: its foot, read to a fraction of a pixel, its shape's own fall below the line taken out (told by four or more prints of its shape on the page), against the straight line through up to five neighbours on each side. One further off than 0.25 pixels and 11.9 times as far as the page's characters typically lie is named, a character set higher or lower, with its offset in pixels and its place: a digit or a letter pasted by hand into a figure or a word about a pixel off. Of 100 characters pasted by hand 0.3 to 2 pixels off their line, 55 could be judged and 11 were named, all of them a pixel off or more; none of 33 pasted in place. On 1,001 honest pictures it named 662 of 173,216 words, about one in 260.

A word off its line by its baseline alone, unlike its neighbours in no other way, is for the record when it lies more than 5 pixels off, its place and offset given: on honest scans such words came on most full pages (2,261 words on 320 of the 977 files of the honest run, the middle one 4.6 pixels off), headings, superscripts and figures of another size among them. Up to 5 pixels, as a word pasted by hand lies, it stays worth a look. A word off its line by its baseline and unlike in another way too, or a character set off its line, stays worth a look. So does a word unlike its neighbours both in how it looks and where it sits. A word unlike its neighbours that lies in running text or boilerplate, read from the page's text there, is for the record (chapter 6, Where a sign lies).

A block of lines set apart together from the lines above and below, by its paper, ink or edges, is for the record, its place given: a shaded row or box of a form sets a block apart so, a band printed in another pass too. On the honest run blocks came on 64 files, and none lay at the place of a forgery.

Strength: Worth a look, never strong. For the record for words off their line by the baseline alone by more than 5 pixels, words in running text or boilerplate, and blocks of lines.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.4 Characters copied, grain and all

To change a figure on a scanned page, an editor copies another character of the page over it, so that the ink and grain match. But a scanner never prints a character twice alike: each print differs in its grain and in where the blur falls on the pixels. The check sets every character beside the others of its shape and names those that share a block of pixels the same, grey level for grey level, with the grain of a print, and those copied and then saved again as a JPEG, which stay nearer each other than prints come. Near pairs of pieces, pairs in running text or boilerplate and the pairs of a page naming more than five are for the record. A stamp or a signature laid on each page by software is the same every time honestly, and clean prints on a page kept as a JPEG can come near each other by chance; those are named worth a look.

A character copied and then the page saved again as a JPEG with its own steps is worth a look. On a page kept as a JPEG, a character that is, to a grey level or so, what a save with the page's own steps makes of another print of its shape laid over it. A JPEG saved again with the same steps comes back as it was, so a character copied from elsewhere on the page comes out as that save makes the copy. The nearest print, moved by up to a pixel and laid with two pixels of paper round it, is saved with the page's table and decoded again. The character is named when it lies half as far or less from that as from the print as it lies and within a quarter of how alike the page's prints are, when none of the other prints of its shape comes so near, and when of 60 characters of its page set beside their nearest print the same way no more than a fiftieth do: where the steps are coarse beside the grain, or prints were drawn alike, any print laid over another comes back as it, and the page is not judged so. Only characters of 100 pixels of ink or more are taken, not prints a whole number of blocks apart. A copy saved by an encoder that rounds otherwise than the trial save, at middling quality, may be missed. The trial saves add about 0.02 seconds to a dense page of 3,500 characters.

A copy of a character, recoloured and turned, with its grain made fainter with its ink, is found by the grain of the paper it carries, its source sought turned up to 15 degrees either way, but only where it holds 16 pixels or more of paper two pixels from its ink: round letters and figures of 40 pixels or more. Copies in body type, copies turned 10 degrees or more, and copies cut out of their paper are missed this way, and are named as a stamp drawn by software when they lie in one. One recoloured lighter than a faint mark and turned is not read at all. A copy whose letter has no other print on the page to set it beside is never taken by its grain: a false strong sign would be worse than the miss.

A character copied and given another ink, darker or lighter, keeps its source's shape and grain with every grey changed by one rule, a darker grey always the darker. Each character of a judged page is set beside the two of its size (within 2 pixels) whose greys follow its own most closely, its ink laid along a straight line through the other's greys, moved by up to a pixel and a half. The line runs through the grey only, never one colour alone: in the colour where an ink is faint, two honest prints in red came as near as a copy. Two are named, worth a look, when the difference left is a third or less of how near the page's characters typically come to their nearest so and within half of how alike its prints of one shape are, and one is half as dark again as the other or more. A copy filled with a flat ink is set beside the others, its source keeping the grain. On the forged-scan set's honest files pairs came as near as 0.14 of the typical, but each of nearly the other's darkness (0.89 to 1.07); a copy made blue came to 0.22, 3.29 times as dark. On 36 honest forms printed in two inks, the same letters in both, none came nearer than 0.42. Strokes alone, pieces of rules and marks wider than a letter (two prints of a word joined by the blur, one in bold, come as near) are left out. A copy whose darkest ink was clipped flat to the new colour no longer lies on one line with its source and is missed. It adds up to about a second to a dense page.

Characters nearer one another than prints are stay worth a look, but three kinds are said once for the record instead, each pair with its place: pairs holding a piece cut at a neck, or a mark wider than a letter; pairs lying in running text or boilerplate (chapter 6, Where a sign lies); and the pairs of a page that names more than five, whose prints come alike as a whole. No forged pair at the place of a forgery was one of them; the fullest forged page whose finding rested on near pairs alone named three. Pairs alike only as each other's nearest, further apart than half of how alike the page's prints are, stay worth a look: a figure pasted by hand lay at 0.57.

Strength: Strong for characters the same pixel for pixel, the grain of their ink too, on a page whose grey levels are not stepped alike. Worth a look for characters nearer one another than prints are, and for the honest causes named in the finding. For the record for near pairs of pieces, pairs in running text or boilerplate and pages naming more than five.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.5 Characters the same pixel for pixel

Characters drawn into a picture by a program, as a picture editor's text tool or an office's stamp software draws them, come out the same pixel for pixel every time, and marks so drawn have no grain of their own. The check names characters that repeat exactly where a program could have drawn them: in an ink or at an angle unlike the page's text, far lighter than it, or on a page whose prints come out alike (a JPEG kept without loss, few grey levels, black and white smoothed, faint grain); and marks without grain that repeat exactly. Honest stamps, light printed forms and a scanner that clips dark ink to one grey make prints alike in the same way, so this is worth a look.

A stamp drawn by software is told from copies of the page's characters by the grain of its ink and of the paper within its figures. In a thin face the ink's core is mostly the stroke's smoothed edge, so the paper decides; on a scan whose paper was whitened it cannot, and such a stamp on a page whose ink strays by 6 grey levels or more is named copies, a strong sign. Real scanners leave 1 to 3 grey levels, where it is worth a look at most.

On a page drawn by a program and saved as a JPEG, characters the same pixel for pixel are worth a look, never a strong sign, when the page repeats its prints so at many places (8 or more moves between pairs besides the pair's own), however wide the pair. A word copied whole blocks of 8 pixels from its source on such a page is named worth a look too; one copied at any other offset stays a strong sign.

On a black and white page, kept as fax (CCITT) or made black and white, three characters or more from one line the same pixel for pixel as as many others, each the same distance away, are worth a look: a word or a figure copied within the page. A character alone the same as another tells nothing there, as honest prints come out alike; a page kept as JBIG2 is not searched, as its coder prints characters of one shape from one print.

Strength: Worth a look.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.6 Text typed into the pixels

Text typed onto a scanned page with a picture editor's text tool is drawn by the program in one flat ink, while every character a scanner prints strays by some grey levels however wide its strokes. The check names words and lines whose characters have no grain of their own. Bold or heavier type, a stamp, coloured ink or a scanner that clips dark ink can look the same, so this is worth a look.

Strength: Worth a look.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.7 Text layer against the pixels

A scanned PDF often carries an invisible text layer, made by reading the page, so that it can be searched. When the picture is edited and the layer is not, the two disagree: the layer holds words over blank paper, or the picture holds words the layer lacks. The check sets each page's layer against its pixels. A layer read badly by the scanner's software disagrees honestly, so this is worth a look at most.

Each word of the layer is set on the picture's pixels. A word of two letters or more and 10 pixels high or more with no ink in its box or within a tenth of its height about it (ink a third of the way from the paper to the page's level of ink, so that grey type counts), or a word of ink the layer passes over standing within 1.5 times the layer's type height of layer words on both sides, is named, with the layer's text and its place: the picture was changed after its text was recognised, a word painted over or one put in. On 30,940 words of honest layers over 60 scanned pages neither was found. A figure changed in place keeps its ink and is not told; nor is a layer whose words were changed and not moved. A page kept in layers (a background picture and the masks of its text) is not judged where another picture lies over the layer's words, nor at all when the picture is drawn through a mask of its own (/SMask, /Mask), nor is a page whose paper is not 40 grey levels lighter than its ink.

Strength: Worth a look. For the record for OCR text over a scan.

Runs on: a PDF. Not run when: no scanned pages or no text layer.

7.4.8 Pieces off the JPEG grid

A JPEG stores a picture in blocks of 8 by 8 pixels on a grid. A piece cut from one picture, saved as a JPEG of its own and laid into another keeps its own blocks, off the page's grid; a piece laid in after the page was saved lacks the blocks the rest carries. The check measures each region's blocks against the page's grid. A region is strong only when another sign agrees on it, since honest software that lays a logo or a stamp on a scan leaves the same; one lacking the page's blocks that no other sign meets is for the record.

A region lacking the blocks the rest of the page carries stays worth a look where another sign meets it: a character of a group of copies, a word unlike the rest, or a region of the other kind. Alone it is for the record, its place given: no value parts such regions on honest scans from pieces laid in, and on the honest run they came on 4 files, and on 2 of them another sign meets one.

Strength: Strong for a region carrying JPEG blocks of its own when another sign agrees on it. Worth a look otherwise, and for a region lacking the page's blocks that another sign meets. For the record for a region lacking them alone.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.9 Regions without the JPEG's traces

Every part of a page saved as a JPEG carries the traces of that save. Paint laid over the page afterwards, or a region pasted from a picture never saved so, lacks them; a page joined from strips can have one strip saved with other tables than the rest. The check measures the traces tile by tile and names regions that lack them or were painted flat. Very smooth paper, or a scanner that sets its quality strip by strip, can look the same, so these are worth a look, and a strong sign only where a copy or a character off its line backs them (below).

A page once saved as a JPEG carries that save's traces in every block of 8 by 8 pixels. Kept without loss since, its frequencies lie near whole numbers; saved as a JPEG again with finer steps, some steps of its lowest frequencies are left all but empty. A region that lacks them was laid in after the first save: a word typed again over healed paper, a stamp, a signature or cloned paper, however well its look, ink and grain match. A part of the page a program drew after the save, as a scanner's own note, does the same. A second save at the same or a coarser quality leaves no such trace, and a page never saved as a JPEG has none to lack. The check adds 0.2 to 0.3 s to a page at 300 dpi, up to 1.2 s for a JPEG whose grid of blocks must be searched for.

Such a region is a strong sign when another measure stands at the same place, within 12 pixels. One is a copy: a character there is nearer a character elsewhere on the page than prints of one character are, its twin away from every such region and off the region's rows, both with the grain of the scan, as a figure copied from the scanned text has its source. The other is a word there that holds a character off its line. Software that stamps a page after it was saved (a received stamp, a PAID mark, a page number, a Bates number, a fax header) leaves regions that lack the traces too, and draws each figure the same every time: on 114 honest pages stamped so, 53 held such a region and 23 of them a copy at it. But a stamp's twins stand in the stamp, within the regions or on their rows, and its characters on one line as they were drawn: none of the 114 drew the strong sign, and none of the other honest files measured holds a region with either sign at it. Eight pasted places of the hand set are strong by it. The finding says which of the two backs each region.

A JPEG saved a second time at the same quality leaves no trace of the first save: decoded and saved again at the same steps its blocks come back as they were, those laid in between and the rest alike (none of either changes, on the 27 such forgeries measured). Saved coarser the second time, the steps' counts alternate, but printed text makes them alternate as far on honest pages saved once (6.2 to 40.4 deviations in the forged boxes' places, 3.8 to 43.3 in the forged boxes). A copy saved as a JPEG on a grid of its own before it was laid in is lost too once the page is saved as a JPEG again: its grid stood 0.55 to 2.71 apart in the region, honest regions of the same pages up to 2.87. None of these is told, and a region laid in before such a save is not named by its JPEG traces. Nor is one told by how its blocks stand up to a trial save at the file's own steps: the page's paper and text move that count far more than a save does. A character copied from elsewhere on the same page is the exception: its source is still there, and a trial save of the source laid over the copy gives the copy back (characters copied, then the page saved again).

Paper painted over is a finding of its own: a region of blank paper, 3 tiles of 16 by 16 pixels or more where text runs (words on both sides, or above and below), keeping a twentieth or less of the spread the page's paper keeps. A white box, or a box or a brush of one colour laid over words in a picture editor, does that. It is worth a look and told only on a page whose paper keeps a grey level of grain (a grey level of spread in the middle tile) and whose smooth paper lies in few pieces (no more than 2 for each thousand tiles). A JPEG of middling quality rounds the grain of plain paper away, and honest pages so smooth held 4.6 to 60 pieces a thousand, painted pages 1.6 at most: they are not judged, and the report says so. A region mostly white on paper nearly white is not taken. Paint at the end of a line, with words on one side only, is passed over as a margin is. A box over one or two figures (under 3 tiles) is missed. A note a program drew, an office's blanking out, correction fluid, a glossy label or a flash's glare gives the same sign. The check adds about 0.04 s to a page of 1240 by 1754 pixels. Of 284 made-up boxes and brushes over words, 118 were named at their place and none elsewhere.

Strength: Worth a look.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.10 Paper copied over paper

A clone stamp or a content-aware fill removes a word by copying paper from elsewhere on the page over it. The paper brings its grain along, and no two patches of a scanner's paper are ever alike pixel for pixel. The check searches pictures kept without loss for patches of paper near the words that match other paper of the page exactly at one shift, or that are pieced together from many small pieces each matching paper elsewhere, as a content-aware fill builds them. A form's printed pattern repeating at one shift matches too, so this is worth a look.

A patch of grained paper near the words alike pixel for pixel with paper elsewhere on the same page, as a clone stamp laid over old characters or a content-aware fill leaves it, is worth a look, never strong. Blocks of 8 by 8 pixels of paper along the lines of words, between their words too, holding no ink and no clipped white are keyed coarsely and set beside one another pixel by pixel; 16 blocks or more matching at one shift of 8 pixels or more make a region, and both places are named with the shift between them. Paper pieced together from many places is named as well: 6 blocks or more within 64 pixels of one another, each the same as paper elsewhere on the page to a quarter of a grey level, at 4 shifts or more, none of them a whole number of blocks either way (paper once saved as a JPEG may keep its grain along a row of blocks only, and repeat along it at any shift). Which of the two is the copy is not told. The search is made on a page kept without loss (one saved as a JPEG before the paper was copied is searched too), whose paper keeps a grey level of grain: a JPEG rounds flat paper to the same few values in its blocks, which then repeat at shifts of whole blocks, so shifts of a whole number of blocks both ways are left out everywhere. A page holding more than 3 million such blocks (some pages at 600 dpi) is said, for the record, not to have been searched. The check adds about 0.5 s to a page at 300 dpi, up to 1 s with grained paper all over it.

Paper patched from paper elsewhere keeps its grain and is not told as paint. It is found as copied paper when the page was kept without loss after the copying, and missed after a JPEG save, on flat or white paper, and where the patch makes fewer than 16 matching blocks at one shift and fewer than 6 pieces from 4 places (a clone stamp's feathered edges leave only its core alike, so a single figure cloned away is often missed).

Strength: Worth a look.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.11 An image generator's pattern

An image generator draws its picture from one eight times smaller, and its decoder leaves a faint pattern repeating every 8 by 8 pixels that changes along rows and columns at once. A scanner, a camera and a JPEG leave none such. The check measures that pattern in the flat parts of pictures kept without loss. A picture tiled with a faint pattern of that size, or a JPEG saved twice on grids out of step, carries one too, so this is worth a look.

The pattern is looked for in the flat parts of a picture kept without loss (a PNG or TIFF, or a scanned page a PDF keeps without loss), faint against the picture's own noise. Paper too smooth to weigh by (its noise smoothed away by a JPEG), or too little of it, is not measured. A JPEG's blocks and a scanner's sensor leave patterns along whole rows and columns, which are not counted; a dither or a half-tone screen is far stronger, and is not taken for one. A picture once saved as a JPEG is not measured, as two JPEG saves out of step make such a pattern; one whose first save left no trace to tell can still be named. Pictures kept as JPEGs, or as JPEGs in a TIFF, are not measured: a JPEG save, or a print scanned again, takes the pattern away. A picture made larger after it was generated is seldom named.

Strength: Worth a look, never strong.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.12 Pictures and marks repeated

No hand signs twice alike and no stamp presses twice alike. A signature or a stamp copied from one place to another is the same in both. The check lists pictures drawn in more than one place and lays the large marks of the scanned pages, those the size of a signature or a stamp, over each other pixel by pixel. Offices lay the same stamp or logo on their letters honestly, so whether the marks should differ is for the examiner to judge.

A picture that is no scan (16 by 16 pixels or more, drawn 24 by 12 points or more) kept the same octet for octet, and drawn alike, in two places or more, by one object or by several, is listed for the record with each place. A signature, a stamp or a seal pasted in as a picture is the same every time it is drawn; so is an office's logo or the signature it keeps for its letters, honestly.

For the marks of scanned pages, the ink of each page, once its words and its rules (runs six times the type's height long and a fifth of the page) are taken out, is joined into marks where it lies within a cell of 4 pixels. Marks twice as tall and as wide as the type or more, no taller than a third of the page, no wider than two thirds, half their cells ink or less (not a photograph), up to 16 a page, are kept. Marks of about one size and alike in 8 by 8 coarse parts, the 4 nearest of each, are laid over each other at the best shift within 3 pixels of laying their corners or middles together, darker than the lighter of their pages' levels of ink. A pair is named, worth a look, when 97% of the pixels inked in either are inked in both and their greys there stray by a grey level or less (97% and 15 grey levels on a page kept as a JPEG, or once saved as one), unless the paper round them, 64 pixels out, is as alike (one scan kept twice), or two on one page stand in one row or one column to the pixel (a form's boxes, a page set by a program). On a page whose grain was not judged (its prints of a character too alike to tell apart, as a page drawn by a program and given grain), only marks the same in every pixel inked in both, 99% of their ink shared, are named. This is done within one file, between pages or on one page, and across files with M-x palimpsest-compare-files. Characters smaller than that belong to the finding of copied characters.

A picture kept twice with other octets (saved again in another way) is not set beside its twin as a picture, only as marks when it is a scan. The marks of a file keep 40 million pixels at most; each mark is set beside 64 of about its size, and 4,000 pairs reading 2,000 million pixels are laid over each other at most. Past them the rest are let go or not tried, and the report says so.

Strength: Worth a look and for the record. Whether the marks should differ is for you to judge.

Runs on: a PDF or a picture file. Not run when: no pictures.

7.4.13 Scan resolution

How sharp the edges of the ink are tells the resolution a page was really scanned at, whatever its file says. A page made larger, or pieced together from scans of different resolutions, shows edges softer than its pixels. The check measures the edges of each scanned page and names the resolution, or says it was made larger. A page blurred, out of focus or printed soft cannot be told from one made larger, so this is for the record.

The finding is for the record only: the page's pixels to the inch from the size the page draws it at, what its JPEG says beside them, and how much detail they hold from the width of its ink's edges. A page whose edges are as sharp as a scan's at the resolution of its pixels was scanned at it, made smaller from a finer scan, or made larger from a lower resolution, as said. A page whose edges are wider than a scan's at the resolution of its pixels holds the detail of a lower resolution: made larger, blurred, or scanned by a scanner whose optics are softer than its pixels, which the edges cannot tell apart. A page made larger by repeating its pixels is named so. A black and white page, or one with too few edges of ink, is said to tell nothing. The check adds about 0.06 s a million pixels to reading a scanned page: 0.18 s for an A4 page at 150 dpi, 0.53 s at 300, 1.8 s at 600.

Strength: For the record.

Runs on: a PDF or a picture file. Not run when: no scanned pages.

7.4.14 Pages kept as JBIG2 symbols

JBIG2 can store a black and white page as a dictionary of character shapes, drawing each character from the shape it is nearest. Such a scanner can put one figure in the place of another, and makes prints of a character the same everywhere, which the copy checks then cannot judge. The check reads only the segment headers and names the pages so kept. This is for the record.

The finding is made when the picture's JBIG2 segments include a text region that refers to a symbol dictionary, so its coder printed every character it matched to a stored shape from that one print. Identical characters there are its design, and any character may have been swapped for one that looks like it as the page was scanned (Xerox WorkCentre copiers turned 6 into 8 in 2013), so neither characters alike nor the digits read on the page can be trusted. Only the segment headers are read, by the lengths they give, never the picture. A page of generic regions alone, or a text region its coder says is lossless, is not named, nor is a page of an encrypted file, whose streams are not decrypted.

Strength: For the record.

Runs on: a PDF. Not run when: no scanned pages.

A scanned word that is unlike its line is never strong: a real scan has such words too. Characters that are copies of one another to the grain of their ink are the strongest sign a scan gives, since no scanner prints a character twice alike. A page printed and scanned again defeats all these signs, because the printer and the scanner lay new ink, grain, edges and JPEG blocks over the whole page, the forged parts and the rest alike. What the new file says of itself and what its words say is then all that is left to judge.

C-c d frames what these checks find in the pixels (chapter 4), and C-c t shows the shapes of the characters beside the report.

7.5 Picture files

These two read the JPEG pictures themselves and run on a picture file, with the second also on the JPEG pictures of a PDF.

7.5.1 A JPEG saved twice

A JPEG opened in a picture editor and saved again is rounded a second time with other steps, and its frequencies no longer fall evenly over the steps of its last save. The check measures how far they stray and names the tables the JPEG uses, those of a common library at a quality or a device's own. A scanner or phone app that saves twice, a viewer that turned the picture, or an honest crop does the same, and it names no place, so it is for the record.

A JPEG saved twice is said for the record when its frequencies fall unevenly over its steps, some all but empty, as a second save with other steps leaves them. It names no place: it tells that the picture was saved again, as a scanner's app, a viewer that turns a picture or an honest crop saves it, and that an edit was possible. The checks of the scanned page say where. It is measured only where enough of its blocks hold no clipped pixel; a second save at the same or a coarser quality is often not told. The JPEG's tables are for the record: libjpeg's standard table at a quality, as most programs write, or a table of its own, as many cameras and scanners keep.

Strength: For the record.

Runs on: a picture file. Not run when: not a JPEG.

7.5.2 JPEG headers and thumbnails

A camera or scanner writes its own make of JPEG header and a small thumbnail of the picture in its EXIF. A picture editor writes another header, and an edit made after the thumbnail leaves the thumbnail showing the picture as it was. The check sets the header beside the device the EXIF names and the thumbnail beside the picture. A picture turned with its old thumbnail kept, or a device unknown here, can differ honestly.

A device named with a program's header is worth a look: the EXIF names a camera, phone or scanner (Make, Model), no picture editor is named, and the header is one a program writes: Adobe's APP14 segment, or a frame other than the baseline one (progressive). The picture was saved again by a program that kept the EXIF. A device's own app that saves again, a gallery, messaging or scanning app, or an honest crop or turn does the same. With an editor named, or a header as a device writes it, the segments, a JFIF segment before the EXIF (which the EXIF standard does not allow, but scanner drivers and phones write as programs built on libjpeg do), frame, sampling, Huffman tables and steps are given for the record. The same holds for a JPEG picture in a PDF.

An EXIF thumbnail unlike its picture is worth a look: the small copy a device keeps in the EXIF, set beside the picture made as small in each of its eight turns and mirrorings, with a lightening or a change of contrast fitted away, is unlike it as a whole (correlation under 0.8), or differs in one cell (a tenth of the picture across) by 20 grey levels or more and 0.4 or more of the spread there: the picture was changed after the thumbnail was made and the old one kept. A thumbnail up to 1024 pixels across or down is read, made no more than 320 across first; a larger one is for the record only. An honest crop or straightening by a program that keeps the old thumbnail does the same; a program that writes a new thumbnail leaves no sign. The place, and the octets to cut the thumbnail out by, are given. Measured on one camera's pictures, 55 honest ones (31 as the camera saved them, 24 saved again whole, turned, lighter or with less contrast) gave 0.966 or more and no cell past 0.22; regions a sixth of the picture across laid in were told in 16 of 18, a sixteenth across in 1 of 6.

Strength: Worth a look. For the record for JPEG metadata.

Runs on: a PDF or a picture file. Not run when: not a JPEG or no JPEG pictures.

7.6 What is laid over a page, and what the file allows

These read what a later save can add on top of a finished page and what the file permits.

7.6.1 Annotations

Annotations are laid over a page rather than drawn in it: notes, stamps, form widgets and boxes. An annotation that looks like the page, a white box over a figure with a new figure on it, can change what a reader sees without touching the page. The check names annotations that look like the page, were added later, are hidden, or are marked for redaction and never applied. Honest reviewers add notes and stamps too.

Text boxes, stamps, shapes, ink and redactions are laid over the page and able to pass for it; they are strong when added later. A redaction marked but never applied leaves what it covers. A hidden annotation has flags that keep it from view.

Strength: Strong for a FreeText, Stamp, Ink, Square or Redact annotation added in a later save. Worth a look for annotations that pass for the page, hidden annotations and redactions not applied. For the record for annotations there from the start.

Runs on: a PDF.

7.6.2 Form fields

A form's fields hold values apart from the page. The check names fields whose values change from one save to the next, and XFA forms, which can show other content than the PDF's own pages. Filling a form in honestly changes its values too; the saves show when and what.

A form field changed between saves means what the form says was changed. What an XFA form shows depends on the program reading it.

Strength: Worth a look.

Runs on: a PDF.

7.6.3 Layers hidden as the file opens

A PDF can hold layers that are off when it opens, so their content is in the file but not shown. Text or a picture can be kept there unseen, or an old version left under a new one. The check names the layers off as the file opens. Drawings and maps hide layers honestly.

Strength: Worth a look.

Runs on: a PDF.

7.6.4 Signatures

A digital signature covers the octets of the file up to its save; what later saves change is outside it. The check reads what each signature claims, whether its octets cover its whole save, what later saves change, and objects hidden in the signed part and brought into use later. Signing more than once, or filling in a form after signing, adds later saves honestly.

A signature is reported as who it names, when, why and how (/SubFilter), approval or certification. It is not checked cryptographically: what is reported is what it claims and what octets it covers. A /ByteRange that stops short, leaves out more than its value, or covers another save than its own means the signature does not vouch for its whole revision. A save after a signature that changes what is shown is strong: the signature does not vouch for what is shown. Annotations, form values, signatures and validation data are reported as allowed or not by the certification's /P. A usage rights signature (/UR3), which a form's publisher writes so that a reader's program may save the form filled in, vouches for nothing the form shows: the publisher's later saves change forms so honestly, and changes after it are for the record. A shadow attack is an object in the signed octets that the signed document does not use, brought into use by a later save (hide, replace, hide and replace).

Strength: Strong for a /ByteRange that is unreadable, leaves out more than the signature's value, stops short or covers another save, for a later save that changes what is shown or makes changes its permissions do not allow, and for a shadow attack. Worth a look for changes after a signature that its permissions allow. For the record for the signatures themselves, and for changes after a usage rights signature.

Runs on: a PDF.

7.6.5 Pages added, removed or moved

Pages can be put in, taken out or put in another order in a later save, and page labels changed to hide it. A page brought in from another document often differs in size or make from the rest. The check sets each save's pages against the save before, and the pages against each other. Documents joined honestly from several files mix their pages too.

A page of another size, rotation or fonts than all the others was put in from another document. Page labels changed means the page numbers a reader shows were changed.

Strength: Worth a look.

Runs on: a PDF.

7.6.6 Actions and embedded files

A PDF can carry JavaScript, actions run on opening, programs to launch, addresses to visit and files kept inside it. None of these is run here; they are named. They can change what a reader sees or hide a document inside the document. Many honest forms carry scripts and links.

Strength: Worth a look for actions that run code or send data and for embedded files added later. For the record for actions that go to places and for embedded files.

Runs on: a PDF.

7.6.7 Encryption

Encryption limits who can open a PDF and what they may do with it. Encryption added in a later save, or permissions changed, tell of a file handled after it was made. The check names the encryption of each save and its permissions. Many honest files are encrypted against printing or copying from the start.

Strength: Worth a look for encryption added later. For the record for encryption from the start.

Runs on: a PDF.

7.7 Beside other files

7.7.1 Beside known-genuine files

A file written again from nothing agrees with itself throughout and leaves the checks above nothing to find. It still differs from what the issuer's own system writes. Given one or more known-genuine files of the same issuer (C-c g, chapter 5), the check reads what that system keeps the same from one document to the next and names each habit in which the examined file stands apart from every genuine file, saying what they do and what it does instead.

Strength: Worth a look at most. Worth a look for a file that names the producer and creator of genuine files and is not put together as they are, for another program named, for other metadata, a later save, another page size, a font or size of text no genuine file uses, a picture kept another way, and text off the grid the genuine files share. For the record for the same program in another version when the file is put together as theirs are.

Runs on: a PDF. Not run when: no known-genuine files given.

7.8 What palimpsest cannot prove

These are the limits of what the checks can say.

  1. An earlier save that was erased without trace cannot be found. A file written again whole, with nothing of the earlier text left in it, has no earlier save to read.
  2. A save hidden inside a stream is inferred from the octets up to a %%EOF that lies in the data. It is worth a look and never more, since nothing in the file names that save.
  3. Attached files are taken at their word only when the document reaches them, their data begins with %PDF- and their own sections list their own objects. Any other stream that holds %%EOF or object headers gets a worth a look. A file attached by a tool that links nothing is such a stream.
  4. Pages are compared by their text and drawing, as the operators say, and not by pixels.
  5. Streams that honestly quote PDF syntax, such as XMP, scripts and fonts, can give a worth a look. Only the first 5 suspicious streams get a comparison of the pages they would make.
  6. When both readings of the last startxref fit, counted from the first octet and from %PDF-, the first octet, base 0, is taken.

Chapter 9 lists what palimpsest does not read at all.

Try it, reading what a check looks for

  1. Examine a PDF of your own with M-x palimpsest.
  2. In * Checks, press TAB to the row of a check and press RET. The help buffer shows the paragraph of that check from this chapter. Press q to close it.
  3. Find a row that says not run and see which reason it gives. Look in this chapter for the check to see which files it is run on.
  4. Find a row with a finding and press TAB to the finding in * Findings. Compare its honest causes with the check's paragraph here.

Examining examples: signed contracts

How a contract comes to be a PDF, and what palimpsest says of each way.

A contract reaches you as a PDF and the question is whether it is what the parties signed. Each way of making and signing a contract leaves a file of its own shape, and most of what palimpsest says only makes sense against that shape. This chapter describes the two shapes of PDF, the common ways of making and signing a contract, what palimpsest says of each, and what it cannot see. The findings below are shown in a short form, as STRONG, LOOK and RECORD for the three strengths of chapter 6, with the page.

8.1 What a PDF holds, in two shapes

A page made by a program (a word processor, a drawing program, a PDF printer). The PDF keeps the text as text: the page's drawing holds runs of characters with their font and place, and the fonts are kept in the file. There is no object for each paragraph or section. Text boxes and lines become runs inside the one drawing of the page.

A scanned page. The PDF keeps a picture of the paper for each page, and a drawing of one line that puts it over the whole page. Everything on the paper, printed text, handwriting and stamps, is pixels in that picture. There are no fonts, unless the scanner read the text (OCR) and laid an invisible text layer over the picture. An office machine saving a compact PDF splits each page into layers: a background picture, often a JPEG, and a black and white mask that holds all the dark ink, kept as JBIG2 or CCITT. The signature is then in that mask, with the printed text, and not apart from it.

So a pen signature is never an object of its own in an honest scan. A signature that is a picture of its own, laid on a page, was put there by a computer.

Poppler's pdfimages -list FILE lists the pictures of each page, their size and how they are stored, pdffonts FILE the fonts, and pdfinfo FILE the creator and producer. palimpsest reads all of this itself. These are quick checks by hand.

8.3 What palimpsest says of each

8.3.1 An honest scan

A scan of a signed contract from an office machine names the machine as the producer and has no creator, one picture to a page and no fonts. palimpsest says, for example:

LOOK    p1  On page 1, a line of the scanned page has no grain of its own:
            drawn into the scan by a program, or in bold or heavier type, or
            ink, a stamp or coloured ink the scanner clipped.
RECORD      The ink's edges of the scanned pictures on pages 1 and 2 are as
            sharp as a scan's at about 300 dpi.

The worth-a-look is a title set in bold: heavy type holds its ink solid, with less of the scanner's grain than the body text. The finding names that honest cause itself. Open the page and look at the line it points to with C-c d: a title, a bold heading or a dark stamp settles it, and an ordinary line of body text would not. The record line says the scan is a real scan at the resolution the file claims. This is what an honest scan looks like to palimpsest: nothing strong, perhaps a look at heavy ink, and the resolution for the record.

8.3.2 A file written in one go

A contract written in a program and exported once, never changed, gets no finding. It is what it says it is, and is the shape to compare the others with.

8.3.3 A scan saved again in a drawing program

Someone opened the scan to join, turn or change it and exported it. The creator is the drawing program, and the pages are still one picture each with no fonts and one save. palimpsest says what it said of the scan and may add:

LOOK    p1  2 characters of the scanned page are nearer one another than
            prints of one character are: copied within the scan and saved
            again, or alike by chance, as clean prints on pages kept as JPEG
            or JPEG 2000, or smoothed, can.

The file's history is gone, so no save, layer or object tells what was done. What is left to judge is the pictures. Two characters alike after a second JPEG save happen. A word or a figure alike pixel for pixel would not. palimpsest does not count a drawing program as the creator of a scanned page as a sign. You should: ask who opened it and why.

8.3.4 A signature picture pasted into a page made by a program

A document made by a program may honestly carry a picture of a signature, and with one picture there is nothing to set it against, for the pictures check compares the pictures of a file with each other. palimpsest finds nothing. It does not say "a signature on a page made by a program". You see it in the structure: pdfimages -list shows one small picture on a page of text, at the signature line. If the contract was said to be signed by hand on paper, this file was not.

8.3.5 Signed later in a PDF viewer

The signature is a picture with its transparency in a stamp annotation, added in a second save:

STRONG  p2  A Stamp annotation (object 82) lies on page 2, added in revision
            2 (the current file): it can look like part of the page, but is
            laid over it.
LOOK        The file was changed after it was first saved: 1 later save is
            kept in it, beside what it changed.

The strong finding is a fact of the file and not a judgment: the signature is laid over the page, in a later save. That is exactly what signing in a viewer does, so it is honest when that is how the contract was meant to be signed. Open revision 1 to see the contract as it was before, unsigned. When the signature was said to be written on paper, it was not.

8.3.6 A page swapped

A page printed again with other terms, scanned in another run and put before the signed page of the first scan, by the same machine, gets no finding beyond those of the honest scan. This is a known miss. Two scans by one machine at one setting look alike to every check, and pages swapped before the PDF was written leave no save behind. What can show it is outside the file: the copy each party kept, the page against a draft or an e-mailed version, the paper. Inside the file, look at each page's angle and paper (the RECORD lines name the resolution of each page) and read the terms against the signed page. Initials on every page are why contracts ask for them.

8.4 Signing services

A contract signed through a signing service or a bank's identity service carries a cryptographic signature: a /Sig field whose octets cover the file as it was signed. palimpsest reads what each signature claims, whether it covers its whole save, and what any later save changed (chapter 7). Signing twice, or a service adding its audit trail, adds later saves honestly. A change to the pages after the last signature does not. palimpsest does not verify the certificate. Acrobat or the service's own check does.

8.5 A checklist

  1. Before palimpsest, ask how the contract was said to be made and signed, and find its row in table 8.1.
  2. Run pdfinfo. Do the creator and producer fit that way? A scan should name a scanner or a scanning app. A drawing program or word processor on a scan means it was opened and exported again.
  3. Run pdfimages -list. One picture per page means a scan. A small picture on a page of text is a pasted signature.
  4. Run palimpsest. Read the strong signs first: they are facts of the file, such as an annotation laid over a page or a page changed in a later save.
  5. Read each finding worth a look with its honest causes, and open the place it names before deciding.
  6. Open each earlier revision and compare it with the last.
  7. Remember what palimpsest cannot see: pages swapped before the PDF was written and a pasted signature on a page made by a program. Compare with the other party's copy when it matters.

Try it, checking a contract

  1. Open a signed PDF of your own, and run pdfinfo and pdfimages -list on it in a terminal. Decide which row of table 8.1 it fits.
  2. Examine it with M-x palimpsest and compare the verdict with what you expected from that row.
  3. If it has a later save, open revision 1 with C-c w and see whether it is the contract before it was signed.
  4. Press C-c d and look at the place each finding names.

Settings and limits

How much of a file palimpsest reads, and what it leaves unread.

palimpsest reads files from anywhere, some made to do harm. Everything it reads is held to a size, so that no file can make it run without end or fill the memory. What it leaves unread, the report says in Not read in the summary (chapter 2). This chapter lists the settings that set the sizes, the limits that are fixed, and what palimpsest does not do.

9.1 The settings

Set them in the package's :config in your init file:

(load-package "palimpsest"
              :source "https://github.com/Tuatara-Editor/tuatara-palimpsest"
              :config
              (setf *palimpsest-most-decoded* (* 16 1024 1024 1024)))

9.2 Each file read shut in

Everything palimpsest reads of a file it reads in a Tuatara of its own, shut in by the sandbox: examining the file, showing one of its objects, drawing a copy of it, and reading it to compare it with others. Each file has a Tuatara of its own, which sees that file, read only, and one directory to write in. It has no home directory, no network and none of your other files. The pictures it turns into pixels are decoded there as well, each by a program held to its own files. It sends back the report's words, its links and the files it wrote, and the editor builds the report from those. Nothing it sends back is run.

Each of these Tuatara may take 1 GB of memory and three times *palimpsest-largest-file* besides, 2.5 GB by default, and may run for *palimpsest-seconds*, an hour by default. A file that needs more is stopped there, and the editor carries on. Its report then says, under Stopped, for example The check of letter.pdf stopped: it needed more than 2,560 MB of memory, or that it took more than the seconds given. What was found before it stopped is not kept. For an object shown or a copy drawn, the message says the same. Raise *palimpsest-largest-file* or *palimpsest-seconds* to give a large file more room, and close the report and examine the file again.

9.3 Fixed limits

These are not settings:

  • at most 5,000,000 cross-reference entries in all the sections of one file, and 1,000,000 from one section;
  • references followed 64 deep, the page tree read 64 deep, a node met twice passed over; a form's fields read 32 deep and 10,000 at most;
  • forms drawn within forms followed 8 deep;
  • at most 2,000,000 operators of one page, and 50,000,000 in all the pages of a file, every save's pages together;
  • a font's ToUnicode map read for 131,072 codes at most, from a stream of 4 MB at most; the XMP metadata from a stream of 16 MB at most;
  • a cross-reference section not where startxref says is looked for up to 64 octets either side;
  • at most 64 cross-reference sections followed by /Prev;
  • at most 100,000 %%EOF lines outside streams read, 500 saves taken apart (*palimpsest-most-revisions*), and 5 saves inferred within streams compared with the save holding them;
  • at most 12 known-genuine files set beside the examined file, their habits read from their first 3 pages; figures set against each other across the first 50 pages of a document.

Past a bound the report says so, under Not read.

9.4 What palimpsest does not do

  • Encrypted files are not decrypted, so their pages' content, fonts and pictures are not read. How the file is put together, its saves and its cross-reference sections are.
  • Signatures are not verified. No certificate or digest is checked. The report gives what a signature claims and which octets it covers. The signer's name is read from the signature's own data, as data.
  • Pictures are decoded for the scanned pages alone: a picture covering a third of a page or more. A JPEG or a JPEG 2000 is turned into pixels in the sandbox. A picture kept as fax or JBIG2 is drawn by poppler's pdftoppm in the sandbox, and one that cannot be read is named in the report. Other pictures are read only as their dictionaries say, and for a JPEG the metadata in its own segments.
  • Text in Type 3 fonts with no ToUnicode map, and text drawn as pictures or shapes, is not read as text. Text drawn as shapes is not measured as ink either: only a scanned picture's pixels are. It shows as shapes the page draws.
  • Figures are read from text, never from pixels. The checks of figures that must agree (check digits, totals, rows, net pay, balances, a figure stated twice, a weekday beside its date) read the text a file holds. A scanned page without a text layer has none, and its figures are not read from the picture: palimpsest runs no text recognition. Where a scan carries a text recognition layer, its figures are checked for the record only, as the layer may misread a digit.
  • Genuine files are set beside the examined file by their habits alone (C-c g, chapter 5): how the files are put together and how their pages are laid out. Their words, figures and pixels are not compared, and no more than 12 genuine files are read.
  • Positions follow the operators: transformations, text matrices and spacing, and the widths each font gives. Clipping is followed as rectangles, the box around each clipping path.
  • What pages draw is checked in the latest revision. The earlier revisions' pages are compared, each with the one before.
  • A field lock is not read on its own. A certification's permissions are.
  • Text is read through each font's ToUnicode map, else its encoding (the standard encodings and /Differences), else shown as the codes themselves in hex (<0041>).
  • Text is covered where the filled shapes drawn after it hide each of its characters: the middle of each, along its own baseline however the text is turned, lying wholly where the shapes of one colour fill. Their outlines (curves cut into straight pieces) are filled row by row, half a point apart, by their fill rules within the outlines they are clipped to. Text is clipped by the box of what it is clipped to.
  • Content credentials (C2PA) are read, not verified. Verifying them would mean checking the COSE signature over the claim, the certificate chain against the C2PA trust list, and the hashes that bind the claim to the file. Their JUMBF boxes and CBOR are read within limits of depth (8 boxes, 24 items), count (10,000 boxes, 200,000 items, each piece of a string counted) and size (64 MB of credentials, 4 MB of text kept, 32 octets of an object identifier). A CBOR map giving a key twice is refused. Past a limit the rest is not read, and the report says why. A WebP or HEIF picture is not examined, so its credentials are not read.

  • A JPEG's header is set beside the device its EXIF names by signs only programs write (Adobe's segment, a progressive frame). JFIF before the EXIF is given for the record, as scanner drivers and phones write it too. No table of devices' own steps is kept: the one published survey (Kee, Johnson and Farid,

    1. keeps its database private, and many devices write libjpeg's standard

    steps, so steps and Huffman tables are given for the record only, and a device that writes one of those signs itself is not known from one that does not. The EXIF is read within its segment, at most 200 entries a directory, each offset checked. Its thumbnail, at most 64 KB lying within the EXIF, beginning as a JPEG does and at most 1024 pixels across and down by its frame, is turned into pixels in the sandbox made no more than 320 across, and set beside the picture at that size, so a phone's 512 by 384 costs what a 320 by 240 does. A frame claiming more is refused for the record before it is decoded. A thumbnail shows an edit only when it is large in it: a region a sixteenth of the picture across is mostly missed. The two pictures are not drawn side by side; the octets to cut the thumbnail out by are given instead.

9.5 Limits of the pixel checks

These bound what the checks of scanned pages and pictures can say.

  • A scanned page's picture is turned into pixels to be examined: one kept without loss is read by the package, a JPEG or a JPEG 2000 by Tuatara's own decoder in its sandbox (ImageMagick or GraphicsMagick under bubblewrap), never in the editor itself. A picture kept as fax (CCITT) or JBIG2 is read by poppler's pdftoppm in the sandbox, from a PDF of that picture alone. One that cannot be read is named for the record, and nothing is claimed of it.
  • A page kept as narrow strips drawn one under the next (of one kind and way up, abutting on the page) is joined into one picture first and named "the scanned page joined from N strips"; places are given in the strip that holds them. Strips that cannot be joined (two pictures at one strip's foot, too many pixels, more than 128 JPEG strips, JPEG blocks on no one grid) are read one by one, or named as not read. JPEG strips saved with other tables than the rest are worth a look.
  • A scanned page is read line by line. A logo, a seal or a signature beside a few lines, whose ink joins their rows, is read apart from them where paper runs down between; a band no such gap parts is left unread, and the report says so. Text far lighter than the page's level of ink (thin type photographed in poor light) is not read at all, and a figure alone in a table's cell is read as characters, not judged as a word. Of 266 places pasted by hand into 19 scanned documents, a word or a character is read at 249. A character's foot is judged only where its shape has four prints on the page and it has three neighbours on its line: 144 of those places.
  • A black and white page (kept one bit a pixel, as fax, JBIG2 and image masks are, holding four grey levels or fewer) holds no grey. Its words are read and judged by how they are turned, but not by their ink, edges or paper, nor by where they sit, which one bit reads too roughly (honest fax pages at 200 dpi set words a pixel or two off their lines). Neither copies of a character nor characters without grain are told on it, as honest prints of a character come out the same pixel for pixel there (up to 89 pairs a page on the honest fax pages, 180 to 338 on JBIG2 pages). Only a run of three or more characters copied together is named. A word typed again in a matching face is not told on such a page.
  • A photograph of a page, as a phone takes, lights, focuses and sharpens each print apart, so that prints of one character seldom come within 30 grey levels of each other; the page is then not judged, and the report says so. Its characters are still set beside one another against how alike its prints are within 60 grey levels, or the prints on their lines where those are more alike (other letters of a word copied with them not counted). A pair is named, worth a look, only when each is the other's nearest, alike to a quarter of that and three times as near as to the next of its shape, both at least half as tall as their page's type. They are also set beside the prints of judged pages, one way, and named when alike to a quarter of that page's likeness. A copy saved again with loss beyond that, one on a line too short to tell, a pair both clipped to one grey (bold type, a monospace column), or one cut apart otherwise than its source (a letter the blur joined to its neighbour), is missed there, and the page's words are not measured for grain.
  • A picture an image generator made is told by its pixels only when it is kept without loss and at the size it was made: the pattern its decoder leaves every 8 by 8 pixels is gone after a JPEG save, a print scanned again, or a picture made larger. Most generated pictures that reach a document are so changed, so a picture with no such finding is not thereby taken from life. Most office scans are not measured at all: their paper is made white to the last grey, and only paper short of white has the flat, unclipped pixels the pattern is read in. So a missing finding says nothing. A dither or half-tone screen on grey paper repeating every 8 or 4 pixels is far stronger than a decoder's pattern and is not named; one made faint enough to pass for it would be. Generated text that does not repeat as type does, blur and grain across a page, and a camera's own traces were measured and do not tell generated pages from honest ones (the numbers are in doc/measures.org).
  • Text written with a chatbot is named only by the words it leaves behind when pasted and not read through. The style of the writing (words chatbots favour, sentences of even length) is not weighed: published detectors that weigh it name honest writers too often, above all those writing in a second language, and none has been measured on Swedish. Nothing in a PDF's structure names a chatbot either: text from one is saved by the word processor or browser it is pasted into. So a page without this finding may still hold such text.
  • Check digits and totals are read from the page's text: the text a born-digital page draws, or the text recognition a scan carries. A scan without text recognition is not read for them. Plusgiro numbers are not checked, for want of a published account of their check digit; the length digit some OCR references carry is not checked either, as the bankgiro allows references without one. The lines of an invoice are not added up, nor the VAT set against its rate.
  • Dates in the text are read in Swedish and English only, and only the document's own date by its label or a letter's date line. A date whose day and month could be swapped (05/03/2024), with a year of two figures, or written in other words (the fifteenth of March) is not read, nor a due date or a period. A date earlier than the file is never a sign, as a copy saved again later is honest; an invoice made out ahead of its date gives the sign honestly. A scan's text recognition may misread a figure, so its dates are for the record only. A date line written with figures alone (2017-11-20 on a line of its own) is not taken, as a due date set apart looks the same.
  • A signature or a stamp copied is found only as a picture laid on whole: the same pixels, moved by whole pixels, neither scaled nor turned. One copied with a scale or a turn, printed and scanned again, laid over other ink (a line, a word) so that its mark joins that ink or is cut where words are taken out, or on a page kept as JBIG2 or drawn by a program, is missed; so is one smaller than twice the type, one copied into the same row or column of its page, and one on pages saved as JPEGs of quality 50 or worse. After a JPEG save the rule is looser, and two scans of one print (a facsimile signature a program prints, a stamp pressed by a machine) whose pixels happen to fall on its strokes within a tenth of a pixel, unturned, come as alike as a copy and are named.
  • A page printed and scanned again defeats the signs read in its pixels. The printer and the scanner lay new ink, grain, edges and JPEG blocks over the whole page, the forged parts and the rest alike, so copied characters, retyped words, paper painted over and the traces of earlier saves are gone. What the new file says of itself, and what its words say, is all that is left to judge.

9.6 What palimpsest cannot see

Palimpsest reads what a file holds. A change that leaves nothing in the file cannot be found, and a careful forger leaves little. These figures come from 87 forged documents made by another hand with other tools, at five levels of care, each beside the honest document it was made from, and 18 honest copies that went through the same tools unchanged (November 2026).

  • Of the 87, palimpsest names the changed place in 36, says something worth a look elsewhere in 29, and says nothing in 22. At the two highest levels of care it names the place in 7 of 36.
  • Of the 18 honest copies, 7 carry something worth a look, and 13 of the 52 honest originals. None carries a strong sign. So worth a look means look, not forged.

What it finds well:

  • A change kept beside what it replaced: a later save, a white box over the old figure, new text in a font the editor brought, a redaction with new text over it. All 4 files changed so with PyMuPDF, and 6 of 13 changed in the page's own stream, are named at the place.
  • A figure changed without those that depend on it. A total that no longer adds up, a net pay that is not the gross less the deductions, a balance that no longer follows from the row before: these show after any printing or saving again. 14 of 22 files with one amount changed are named at the place.
  • Pages put together from two exports, and a file changed where it lay after LibreOffice wrote it.

What it finds badly or not at all:

  • A change made in the program that wrote the document, or by writing the page again with the font's own characters, every dependent figure worked out again: the file is then an honest file of other content. Draw 3 of 10, qpdf 1 of 4.
  • A document printed to PDF after the change (Chromium, CUPS, Ghostscript, cairo) or drawn again by Inkscape: the printing writes every page anew. Only figures that do not add up are left.
  • A forgery flattened, printed and scanned again: 2 of 8. The scan's pixels hold the paper, not the edit; nothing local is left to find.
  • A number, an address or a name changed with care: 3 of 18 and 1 of 5. No sum depends on them.
  • Metadata written back to what the original said, when the file was written again afterwards.

Beside known-genuine documents of the same issuer (C-c g, chapter 5) the same files say more. Of the 81 forged files that had such documents to stand beside, the comparison alone names 60 as not the issuer's own, each worth a look. With every check together, 5 of the 87 are then left with nothing said, in place of 22. The price is that the comparison cannot tell a changed file from one only written again: of 17 honest copies that went through the forgers' tools unchanged it names 14. For that reason it never makes a strong finding. It says the file is not as the issuer wrote it, which is true of them. Of 143 genuine documents set beside others of their own issuer and template, it names none.

What stays unseen even so: a scan changed in its pixels and put back in the scanner's own file, a page changed where it lay with the font's own characters, a document made again in the issuer's own program. 21 of the 81 are such files.

An honest-looking report is therefore no proof that a document is honest. Set the document beside its source where there is one: the issuer's own copy, the bank's record, the register.

Every command and setting

Each command and setting of palimpsest, to look one up by name.

The tables are made from the program each time this manual is made, so they never list a command or setting that palimpsest does not have. The first table has four columns. The first two are keys: the modal keys, which work only with modal editing on, and the non-modal keys, which work with it off too. A command with no key says M-x and its name in the second column, because you can only run it by its name. The third column is the name of the command and the fourth says what it does.
